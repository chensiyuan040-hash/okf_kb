# 建库指南 — 从原料到 OKF 知识图(定稿)

> **本版为终态架构(2026-09-24 封版),后续勿再回摆。**
> 三轮调整的结论沉淀:A(两工具组合)→ B(pi-llm-wiki 单轨)→ C(本版=A 的定稿规范版)。
> B 阶段的实测贡献:证明了砍掉 iwe 会丢图查询与体系显式性,并纠正了成本误判
> ("双状态"实为"一源两读者"——iwe 的图是从 md 解析的投影,不持有第二份事实)。

## 0. 架构:一源两读者

**建图者是 LLM,不是工具。** 提取、分类、综合、链接全是模型干的语义活;
工具兜机械错误,兜不住语义错误——**建图质量上限 = 跑 ingest 的模型上限**。

**事实源只有一个:一批 markdown 文件**(wiki/ 下的知识页 + raw/ 源包)。
两个工具是同一批文件的两个读者,各管一半能力,没有第二份要维护的数据:

```
                    ┌─ wiki/*.md(知识页)+ raw/*(不可变源包)─ 唯一事实源 ─┐
                    │                                                      │
        pi-llm-wiki(写侧+生命周期)                          iwe(结构读取+校验)
        ├ capture/ensure_page 写页                          ├ 解析链接 → 体系树/图(投影)
        ├ events.jsonl 事件溯源 → registry/backlinks        ├ tree / find:图查询
        ├ lint 治理                                          ├ retrieve:带体系语境消费
        └ qmd BM25 → recall/search(消费主通道)             └ schema validate:OKF conformance
```

- **pi-llm-wiki**:页面生命周期管理(capture→建页→治理)+ 词法检索。所有写入必须走它的工具(事件溯源)。
- **iwe**:只读结构层。`.iwe/` 里只有 `config.toml + schemas/`(校验配置),无数据副本;树和图是每次从 md 解析出来的。
- **一个动作两家用**:在枢纽页写一条"独占一行链接",对 pi-llm-wiki 是合法互链(lint 可查),对 iwe 是 inclusion 边(体系树可查)——已实测两种路径形态(`/concepts/x.md` 绝对、`concepts/x.md` 相对)均正确识别。

## 1. 蓝图四模块流程(端到端)

外网只是进料口;模块 1→3 在内网建库侧完成,模块 4 是内网消费侧。

| 模块 | 做什么 | 谁做 | 工具 | 产物 | 完成判据 |
|---|---|---|---|---|---|
| **0 进料**(前置) | 外网资料收集,git 带入内网 | 人/外网会话 | git | `raw-inbox/` 原料 | 原料进仓 |
| **1 raw sources** | 原料 → 不可变扁平条目 | 建库会话 | `wiki_capture_source` | `raw/sources/SRC-*/` | 每份原料有 SRC 编号源包 |
| **2 wiki** | 建页、互链、**挂体系**、回源 | 建库会话(LLM 建图) | `wiki_ensure_page` + 挂载规范(§2) | 知识页 + 体系枢纽页 | 每页 ≥2 出链+回源;新概念挂上枢纽;iwe tree 能看到体系 |
| **3 schema** | 宏观规范与治理 | 建库会话 + 人工抽查 | `wiki_lint` + iwe `schema validate` + iwe `tree/find` 复核 | 零告警的库 | §6 checklist 全过 |
| **4 consumer** | 内网弱模型只读消费 | 消费会话 | `wiki_recall`/`wiki_search`(主)+ iwe `retrieve`(可选) | 按需检索结果 | 能 recall 出相关知识页 |

**更新双通道主次**(2026-11-03 钉死):同一对源(Confluence/NextCloud)存在两条更新通道——
**pipeline 自动线(`dispatch run` + systemd timer)为主**,日常增量无人值守(水位线增量、质量门、自动 commit、告警兜底);
**kb-sync 会话工作流(`/kb-sync-confluence|nextcloud`)为辅**,用于冷启动全量、存量重灌、涉密 BM 源等人工场景。
两通道的机械原子(API 形态/认证/CQL 翻页/PROPFIND 解析/ETag 清洗)**已收编 `tools/sources/common.py` 单一实现**——改源 API 形态只改这一处,Cloud/DC 由 `CF_API_SHAPE` 选择;增量状态机仍是两套设计(游标+身份索引 vs 水位线+keymap)、游标互不感知,先后跑同一源时靠 capture 内置 md5 去重门防重复进料;**同一库避免两通道并行混跑**,以 pipeline 水位线为准。

日常增量循环(时序):

```
raw-inbox 新原料(git 带入)
   │ ① capture:wiki_capture_source → 不可变源包 raw/sources/SRC-*/
   │    (已知出处必带溯源参数 origin_url/author/source_system/source_updated_at → 自动落 manifest+source 页
   │     frontmatter;管线捕获自动从 connector 元数据透传;存量库回填:建库会话批量给
   │     source 页 frontmatter 补这三行,Confluence 可按 pageId 构造 url)
   │    (capture 已内置精确去重门(2026-10-15 补丁):text/.md/.txt 输入与已有源包逐字节比对,相同即拒并报出已有 SRC;url/非文本文件靠巡检兜底;查重纪律(title/关键词)仍保留作第二道——去重门只拦"完全相同",改写过的近似重复仍需查重纪律与归并;
   │     已有同内容 source 页则跳过,防重复进料;**capture 成功后把 raw-inbox 原文件
   │     移走**(如 raw-inbox/done/),残留文件会被下次会话再 capture;漏网的重复包由
   │     巡检"重复源包"检测兜底(extracted.md 内容相同即报);ingest 时同结论的重复
   │     SRC 合并进同一概念页、回源并列,不写演进——演进只留给结论变化)
   ▼ ② ingest(LLM 按 SKILL.md 纪律)
   │    wiki_search 先搜后建,命中页 wiki_read 读过后再定合并/新建(防分叉,§3 纪律3)
   │    填 source 页:去 [LLM: 占位] 写 Summary/Key Takeaways + Key Terms 术语清单,status→draft
   │    wiki_ensure_page 建 entity·concept·synthesis 页(已存在则只返回路径,不改内容)
   │    更新已有页内容 = 建库会话直接编辑该 md 文件(实测:词法索引即时反映,无需 reindex;
   │    "绕过工具手写"仅指新建页——registry 不收,检索不可见)
   │    同主题新旧结论 → 合并演进小节(标题固定 ## Evolution,条目以 ISO 日期开头,
   │    按事件时间排序、SRC 日期兜底,旧标已过时);entity 页首行写别名
   │    commit 前输出归并清单(每条 SRC 一行,人扫一眼抓分叉)
   │    正文互链(行内)+ 回源;新概念到枢纽页加独占行链接(挂体系,§2)
   ▼ ③ 治理:wiki_lint(断链/孤儿/歧义)+ iwe tree/find 复核体系完整性
   ▼ ④ OKF 检验:iwe schema validate(okf/okf-log)+ wiki_status 复核
   ▼ ⑤ git commit(存储与版本;raw 不可变由纪律+guard 保证)
   ─────────────────────────────────────────────▶ ⑥ 消费(recall/search;按需 retrieve)
```

## 2. 体系挂载规范(核心规定)

蓝图"多个有向图"的落地 = **每个知识体系一个 synthesis 枢纽页,成员靠独占行链接挂载**。
一页被多少个枢纽收录,就在多少个体系里,文件只有一份。

**边的语义(三种,由写法区分)**:

| 写法 | 语义 | 谁消费 |
|---|---|---|
| 独占一行 `[成员](/concepts/成员.md)`(在枢纽页里) | **inclusion**:体系归属(父包含子) | iwe tree/find;llm-wiki 当普通互链 |
| 正文行内 `[相关](/concepts/x.md)` | **reference**:引用(不构成树) | backlinks;iwe 当 reference 边 |
| `[source](/sources/SRC-*.md)` 回源 | **provenance**:知识出处 | OKF 信任信号;两工具都读 |

**枢纽页写法示例**(`wiki/syntheses/运维排障体系.md`;目录均为复数:
concepts/entities/analyses/requirements/syntheses/sources):

```markdown
---
type: synthesis
title: 运维排障体系
created: 2026-09-24
---

本体系收录排障路径相关知识。依据:[source](/sources/SRC-2026-09-24-002.md)

[网络类排障](/concepts/网络类排障.md)

[数据库类排障](/concepts/数据库类排障.md)

[排障通用方法论](/concepts/排障通用方法论.md)
```

(frontmatter 由 ensure_page 自动生成;content 不必写 H1,标题在 frontmatter title)

> ⚠️ **塌平警告**:上面这个示例就是"修好"的形态——三个成员链接全部**独占一行**。
> 枢纽页里写成员的三种写法对照:

| 枢纽页里的写法 | iwe 判读 | 结果 |
|---|---|---|
| `[成员](/concepts/成员.md)` —— **独占一行** | inclusion 边 | ✅ 成为体系成员(`iwe tree/find` 可见) |
| `- [成员](/concepts/成员.md)`、`- [[concepts/成员]]` —— **列表格式** | 不构成 inclusion 边 | ❌ **塌平**:渲染看起来像成员,树里没有 |
| 行内 `……参见[成员](/concepts/成员.md)。` | reference 边 | 普通引用,不算成员(归属只由独占行链接表达) |

依据(iwe 官方文档 `docs/iwe/inclusion-links.md` 原话):"An inclusion link is a
markdown link placed on its own line." 真实库 10 个体系页踩过塌平坑;此后由
`tools/okf-tidy/vault-health.mjs` 检查项 2 实时检出,并可用树基线存档 + diff 守护
(见 `tools/okf-tidy/README.md`)。

**成员页写法示例**(`wiki/concepts/网络类排障.md`):

```markdown
---
type: concept
title: 网络类排障
created: 2026-09-24
---

正文:网络排障的知识内容……属于[运维排障体系](/syntheses/运维排障体系.md)。

依据:[source](/sources/SRC-2026-09-24-002.md)
```

规则:
1. 挂载链接**统一用 llm-wiki 风格**(绝对路径带 `.md`,如 `/concepts/x.md`),一个写法两家用;
2. 成员页行内回链枢纽(表达"属于",不构成反向树);
3. 独占行链接**只写在枢纽页**(体系归属是枢纽的职责),成员页之间用行内互链;
4. 体系划分按**消费场景**建(排障树/新人上手树/产品知识树),不按部门复制内容——条目一份,视图多份;
5. **新体系枢纽必须在根 `index.md` 追加一条独占行链接**(否则 iwe tree 从根看不到该体系);
6. 注记:iwe tree 的显示标签读 H1,而 ensure_page 生成的页无 H1(标题在 frontmatter),
   树节点会显示空标签——结构无碍,以 `find --filter` 的输出为准。

## 3. pi-llm-wiki 工作流(15 工具分组)

**建库会话**(写侧,集中在上游管线):

```
一次性:  wiki_bootstrap                 建库(目标目录开会话跑一次)
管线:    wiki_capture_source            原料 → 不可变源包(模块1)
         wiki_ingest                    自动 ingest(需配 task model;不配就手动走下行)
         wiki_ensure_page               建知识页(唯一合法的新建方式);更新已有页=直接编辑文件
         wiki_lint                      治理(断链/孤儿/歧义/矛盾)
治理修复: wiki_rebuild_meta / wiki_reindex / wiki_reindex_embeddings
         wiki_status                    体检(页数/索引状态/诊断)
记录辅助: wiki_retro / wiki_log_event / wiki_observe
```

**消费会话**(读侧,内网 agent 只给这组):

```
wiki_recall   语义召回(CJK 词法,links-first 防上下文爆炸;命中 source 页直接带溯源四字段 origin_url/author/source_system/source_updated_at,引用不必二次 read;引用纪律=逐字复制字段、缺失报"来源未登记"、禁止借用他页或拼造——弱模型必配)
wiki_search   registry 精确搜
wiki_status   只读体检
```

**不用/慎用**:`wiki_watch`(长驻监听)、`wiki_reindex_embeddings`(需向量模型,内网离线不可用,词法已够)。

**引用统计**(2026-11-03 起,bundle 第十一处补丁):`wiki_recall`/`wiki_search` 每次调用自动落一行到 `meta/retrieval-log.jsonl`(零命中也记,是知识缺口信号;只读消费进程记 `ro:true`,建库自查询记 `ro:false`,口径可分)。查看走 `wiki_stats`(Top-N 命中页/最近 query/zero_hit_pages;**不在消费只读面**,用建库会话或 `python -m pipeline.manage call wiki_stats --json '{}'`);日志是纯运营数据,已进 gitignore,删了不影响任何功能。巡检可关注 zero_hit_pages(从未被检索的页)与高频低分页。

**纪律铁律**(给弱模型时要反复强调):
1. **raw 不可改**,meta 是生成物不手编(接 guard 钩子机械拦截);
2. **新建页必须走 `wiki_ensure_page`**——registry 是事件溯源,绕过工具手写新页进不了图谱,search/recall 完全不可见(实测:`reindex all+force` 也救不回)。**已存在页的内容更新**则相反:直接编辑文件即可(ensure_page 对已存在页只返回路径不改内容),索引即时跟随;知识演进(结论变更)在页内加"演进"小节,旧结论标"已过时"+双 SRC 回源,不删页;
3. **先搜后建,先读后并**(防概念分叉与新旧分叉,SKILL.md 工作流第 6-7 步):
   - 建页前 `wiki_search` 主题,命中页**必须 `wiki_read` 看过内容**再决定合并还是新建——
     比对材料摆在眼前,弱模型也能判断;只看标题列表判断必分叉;
   - **判据:两份 source 回答同一个问题 / 描述同一个对象 = 同一主题**,合并进同一页
     (直接编辑文件)加演进小节。**演进小节格式是硬约束:标题固定写 `## Evolution`**
     (消费端工具按这个字面量找历史;中文标题它不认),**每个条目以 ISO 日期开头**
     (`- 2026-10-12: 结论…`,别的日期写法都无法比较大小)。**排序用事件时间优先**
     (文档自身声明的日期:纪要落款/ADR 日期/决策日期),文档没写才退回 SRC 入库日期——
     **补录旧料时入库顺序会骗人**(8月决策 10月才补录,按 SRC 排会错判为新);现行结论在
     正文,旧的标"已过时";**页的事件时间 = 演进条目里的最新日期**(消费端裁决用);
     不确定时**倾向合并**——分叉代价远大于页稍长;
   - **entity 页正文首行写 `Aliases:`** 列出所有见过的写法(order-service / ordersvc /
     订单服务)——别名进正文才进词法索引,跨名称的同一实体靠它命中;新料用别名拼写时
     必须归并到已有 entity,禁止另建;
   - **commit 前输出归并清单**(每条 source 一行:`SRC → 合并进某页(演进)` 或
     `SRC → 新建某页`),人十秒扫一遍——分叉在这里被人眼抓住,不用等 lint 报警;
4. 每页 ≥2 出链 + 回源(上游 SKILL.md 原纪律:RAW IS IMMUTABLE / CROSS-REFERENCE EVERYTHING);
5. 新概念必须挂到对应枢纽页(§2 挂载规范);
6. **source 页整理完 = status: skeleton→draft**(okf.yaml 只认 draft/stable/deprecated,
   skeleton 在 conformance 报错就是"这页没整理完"的提醒——这是有用的牙齿,别放宽 schema)。

### 替代工作流:deprecated 三件套(新旧交替时)

知识被新页取代时,三处改动**在同一批操作内完成**(分开做 = 中间状态无标注,消费侧读不出替代关系):

| 角色 | 动作 |
|---|---|
| 旧页 | frontmatter 写 `status: deprecated` + `superseded_by: <新页ID>` + `stale_after: <日期>`;正文开头引用块加"本方案已被《新》替代" |
| 新页 | frontmatter 写 `supersedes: <旧页ID>`;Summary 声明替代关系与生效时间 |
| 概念页 | "版本历史"一节:当前版本(依据新页)+ 历史版本"已作废"(依据旧页)——唯一被两轮验证证明可靠的机制 |

消费侧效应:替代完成后 `wiki_recall` 返回的旧页条目自动带 `flags`(`superseded` + 可能的
`stale`,见 §8 补丁清单),弱模型不读全文也能看到"该条已被替代"的结构化提示——
SPEC §11 "SHOULD surface, not silently drop" 的落地。真实库当下 112 个源页全部 stable,
第一次"替代"尚未发生——本规范是防带病发生的闸门。

> 本机实测(隔离克隆库,2026-10-13):三件套字段构造后 `wiki_lint` 零异常;`flags`
> 三 kind 各页可见;检索分数与排序不受影响。

### 操作手册(六条,踩过的坑)

1. **采集超时 ≠ 失败**:`wiki_capture_source` 报超时后**立即查库分辨**——源包写入了 =
   已成功(资料在);不要盲目重试(会留重复源包)。
2. **手工改动"认内容不认记录"**:已注册页改正文**即时生效**(检索实时读文件——实测:
   改正文后不 rebuild,recall 直接命中新词);但事件台账(events.jsonl)不会记录手工改动,
   追溯断链。纪律:编辑走受控路径;留痕靠 git(可选增强:`tools/okf-tidy/install-hooks.sh`
   把"靠 git"变成机制)。
3. **库外新增页面文件必须 `wiki_rebuild_meta` 后才可检索**:registry(meta/registry.json)
   是"参与检索的页清单",收编库外新文件靠 rebuild_meta 重建清单——实测:手写文件放入
   wiki/ 后 recall 空 → rebuild_meta → 命中;已注册页改正文则反之即时生效(见第 2 条)。
   即便被收编,绕过工具写的页无事件溯源——纪律不变:页走工具写(铁律 2)。
4. **validate 报错 = 待整理清单,不是库损坏**(问题 17):`iwe schema validate` 的报错
   指名道姓列出文档/字段/原因——它本身就是待整理清单,比一句"校验失败"好用。`skeleton`
   是摄入机制的开关(改掉会破坏跳过判断),schema 保持 OKF 词表不放宽。批次门禁
   `tools/okf-tidy/gate.sh` 把报错翻译为"以下页面未整理,请整理后重新提交"并卡住批次。
5. **采集前撞题预检**(问题 6 预防面):采集新资料前,先用标题关键词 recall 一次——
   命中既有 stable 页时先判断"更新还是新增",避免无标注的双版本并存(漏判的会进入
   `vault-health` 的"疑似版本对"清单,人工逐对确认)。
6. **整理完成 = 三件全清**(与 `vault-health` 检查项 1 同口径):①去占位符(正文无
   `[LLM: …]`)②补链接(至少一条入链或出链;孤儿由 `wiki_lint` 孤儿清单判)③status 改
   draft。三件全清的页才过批次门禁;`status: skeleton` 或残留占位符 = 未整理,检索侧
   以 `flags: [{kind: "skeleton"}]` 标记呈现(§8)。

## 4. iwe 工作流(只读结构层,四个用法)

```bash
# 一次性脚手架(建库后跑;保留 .iwe/{config.toml,schemas/} 即可,无数据副本)
cd <vault 根>/.llm-wiki/wiki     # OKF bundle = 知识页目录,iwe 在这里初始化
iwe init --okf          # OKF 链接形态 + 根 index.md(okf_version: "0.2")+ 三 conformance schema
# ⚠ init 后必做:注释掉 config.toml 里的 [schemas.okf-index] 绑定——
#   llm-wiki 自动维护根/目录 index.md(## Directories 等形态),与 OKF §8 index
#   形态天然冲突,校验它必报错;okf-index 收窄不校验,okf-log 保留(llm-wiki
#   的 log 形态恰好合规)

# 治理查询(建库会话,每次批次后)
iwe tree                                       # 体系全貌:哪些体系、各挂了哪些页
iwe find --filter '$includedBy: {match: {type: synthesis}}'   # 某体系全体成员
iwe find --filter '$referencedBy: {match: {type: concept}}'   # 谁引用了某概念

# 消费(可选通道:带体系语境)
iwe retrieve -k <页key> --expand-included-by 1  # 页内容 + 父级体系语境注入

# 校验(§6)
iwe schema validate
```

**不用**:normalize(除非迁移期,先 `--dry-run`)、extract/inline/squash(文档编辑类,知识库不用)。

**pi-llm-wiki 侧参数注意**:`wiki_reindex` 内网**不要 `scope:"all"`**(all 含向量组件,
会去拉 node-llama-cpp,内网没有且不装)——用默认 changed 或显式 components 只要 lexical。

## 5. 起步路径

**从零建库**:目标目录开会话(MCP 已接)→ `wiki_bootstrap` → `iwe init --okf`(在 `.llm-wiki/wiki/` 里跑+收窄 okf-index,见 §4)→ 按 §1 循环。

**从存量 wiki 迁移**(我们目前的情况):
1. 有导出/API 就走导出(别写爬虫,除非只有 web 界面);
2. **原目录树别丢**——分类节点逐个翻译成 synthesis 枢纽页,原父子关系翻译成独占行挂载链接,原导航树零成本变成初始体系;
3. 导出文件进 `raw-inbox/`,批量 `wiki_capture_source(file_path)`;
4. 剩下走 §1 模块 2→3。

## 6. OKF 格式检验(模块 3 验收)

SPEC §11 三规则:非保留 `.md` 必有可解析 frontmatter、必有非空 `type`、`index.md`/`log.md` 按 §8/§9 形态。

| # | 检验项 | 怎么验 | 依据 |
|---|---|---|---|
| 1 | frontmatter 可解析、type 非空 | `iwe schema validate`(okf.yaml) | SPEC §11.1-2 |
| 2 | log.md 形态 | 同上(okf-log;index 形态不校验——okf-index 已收窄,§4) | SPEC §11.3 |
| 3 | trust/provenance families 良构 | 同上(status/stale_after/verified/sources) | SPEC §5 |
| 4 | 根声明 okf_version: "0.2" | `iwe init --okf` 生成,人工确认在 | SPEC §12 |
| 5 | 断链/孤儿/歧义链接清零 | `wiki_lint` | 模块 3 治理 |
| 6 | knowledgeFormat 与诊断 | `wiki_status` → `okf-0.2` + blockingDiagnostics 空 | vault config |
| 7 | 体系挂载完整(新页都在树上) | `iwe tree` 对照;`find` 查无主页 | §2 挂载规范 |
| 8 | 每个知识页有回源引用 | 人工抽查(synthesis 层) | provenance |
| 9 | raw 未被改动 | git diff | 不可变纪律 |

## 7. 质量策略(内网模型能力有限的前提下)

| 手段 | 兜什么 |
|---|---|
| SKILL.md 纪律常喂给整理模型 | 流程性错误(漏引用、重复建概念) |
| **source 页 Key Terms 术语清单**(SKILL.md 工作流第 5 步) | **检索层信息丢失**:索引只覆盖 wiki 页,原文细节词不写进 source 页就 recall 永远查不到(2026-10-10 实验:BM25/reranking 仅在 raw → 零命中) |
| iwe schema 收紧(maxTokens 限页大小) | 弱模型写大而深的页易失控 |
| wiki_lint + schema validate + tree/find 复核 | 机械错误(断链/孤儿/格式/漏挂) |
| synthesis 页人工抽查 | 语义错误只在这一层人审 |
| 人审确认即盖 verified(SPEC §5.2 形态 `{ by: human:<id>, at: <ISO datetime> }`,裸日期会被 iwe schema validate 拒) | 知识腐坏可检测(巡检报超期) |
| raw 不可变 | 整理不满意换更强模型重跑,原料永在 |

## 8. 消费(内网 agent)

- **主通道**:`wiki_recall`(CJK 词法召回,links-first 防上下文爆炸)/ `wiki_search`;
- **读全文**:`wiki_read`——recall/search 只返回 preview 片段,定位到页后用返回的
  page_id 调 `wiki_read` 读整页(frontmatter+正文);长页自动分页(默认窗口 6000 字符,
  响应头带 `has_more` 和续读 offset)。**标准消费流:recall 定位 → wiki_read 读全文**;
  page_id 以 `raw/` 开头时可读源包原文件(如 source 页 frontmatter 里 `raw_path` 指向的
  `raw/sources/SRC-xxx/extracted.md`),同样走分页窗口,防弱模型一次吃下长原文;
- **消费纪律四条**(抄进消费 agent 的提示词;wiki_read 的工具描述里已内嵌同款,
  这是弱模型的显式强化):
  1. **preview 只选题,答题必读全文**——recall 的 ~120 字符预览只用来决定读哪页;
  2. **冲突裁决**:多个页/来源结论打架时,按**事件时间取新**——页的事件时间 = 其
     `## Evolution` 小节条目中的最新 ISO 日期,无演进小节才退回 SRC 入库日期,比大小即可,
     无需业务理解;页内有演进小节时,**正文=现行结论,演进=历史**;**时点问题**(问
     "上个月/9月时用的什么")取**日期早于该时点的最新演进条目**作答,不是一律给现行;
     长页演进小节在末尾,记得按 has_more 翻页读全;即使建库归并失手分了叉,这条让消费端
     照样答对;
  3. **深挖路径**:概念页不够 → source 页摘要 → 仍不够按 raw_path 读原文(分页翻);
  4. **回答标注出处**(依据:concepts/xxx)——人一眼可核实,也最便宜地暴露幻觉;
- **可选通道**:iwe `retrieve`——需要体系语境注入时用(把父级体系上下文一起带给弱模型);
- **工具面收窄(只读模式)**:消费会话的 MCP 配置加环境变量 `LLM_WIKI_READ_ONLY=1`,
  server 只注册 4 个只读工具(wiki_recall / wiki_search / wiki_read / wiki_status),
  写侧工具**物理不注册**(tools/list 里看不到,沙箱 agent 无法绕过)。wiki_lint 不在
  消费面——它带 auto_fix 写能力,治理/体检走本机管理通道(`python3 -m pipeline.manage`,
  直调 bundle stdio,不经平台 HTTP)。
  建库会话不设此变量,保持全工具。**必须配这一项**——实测不设时消费 agent 会拿
  wiki_capture_source 绕路复制源包,污染事件流。
- **消费纪律卡片**:五条硬纪律(recall 定位→read 全文、废弃/过期字段必提示、跨库条目必
  过滤、矛盾不裁断、skeleton 页禁用作内容)见 [`消费协议卡片.md`](消费协议卡片.md)——
  整卡贴进用库 agent 的系统提示/会话开头模板。

> `wiki_read`、`LLM_WIKI_READ_ONLY`、`LLM_WIKI_HTTP`、recall/search 条目的 `flags`
> 生命周期标注(含 `skeleton` kind)、`wiki_lint` 明细化(未整理计数 + 孤儿/缺失页名直出、
> 非 `--fix` 也落报告)、capture 去重门+溯源参数、**建库写门 buildGate**(vault 开
> `buildGate: true` 后写工具按 okf-ops 会话状态机放行/拒绝,无锁与冻结期物理拒写)是本
> 仓库对上游 bundle 的**功能补丁族**(上游 recall/search 均只返回 preview、不 surface
> 过期/废弃/未整理状态,且无只读/HTTP 模式;lint 只报计数不出页名、非 `--fix` 不落报告
> 文件;上游无任何会话门禁概念)。升级重打 bundle 时会丢失,需逐项回放——完整清单、
> patch 位置与重打冒烟见 `tools/pi-llm-wiki/CHANGELOG.md`(`mcp-smoke.mjs` 三轮断言
> 工具面/只读面/写门三态)。
>
> 库整理与门禁工具组(体检 / 批次门禁 / 留痕钩子)见 `tools/okf-tidy/README.md`。

### 集中部署(C/S,可选)

多台机器的消费 agent 共用一个库时,不必每台都 clone vault——在内网服务器上把 server
跑成 **HTTP 常驻服务**,客户端只填一个 URL:

```bash
# 服务器侧(systemd 常驻):
WIKI_ROOT=/data/vault WIKI_HOME=/data/vault LLM_WIKI_READ_ONLY=1 \
LLM_WIKI_HTTP=1 LLM_WIKI_HTTP_PORT=8901 LLM_WIKI_HTTP_HOST=0.0.0.0 \
  <仓库>/tools/node24/bin/node <绝对路径>/mcp-server.mjs
# WIKI_HOME 必须与 WIKI_ROOT 同值(关闭 recall 个人库合并的唯一防线;bundle 对未设置者自动同置兜底)
```

```bash
# 每台消费机器:
claude mcp add --transport http llm-wiki http://<服务器IP>:8901/mcp
```

- **stateless Streamable HTTP**:每个 POST 独立处理(无 session),实测 10 并发正常;
  `LLM_WIKI_READ_ONLY` 在**服务端**配死,客户端想绕都没门;
- 默认监听 `127.0.0.1:8901`,跨机访问设 `LLM_WIKI_HTTP_HOST=0.0.0.0`;
  HTTP 无内置认证,跨机建议反代加 basic auth/TLS(iwec 同款建议);
- **建库会话仍走 stdio 本地跑**(写集中),HTTP 只服务消费;
- transport 类来自随行文件 `mcp-http-deps.mjs`(自包含单文件,与主 bundle 同目录,
  勿分离)。

## 9. 保密库(secret-vault,保密文档专用)

保密文档(涉密/敏感资料)不得以明文形式保存在文件系统——本章是保密库的日常 SOP;
完整设计(泄漏面盘点/威胁模型)与操作手册(异常恢复/备份带出)见
[`tools/secret-vault/README.md`](../tools/secret-vault/README.md)。

**核心约束**:保密文档从进入系统到建库、检索、会话结束,**明文只存活于内存盘(tmpfs)**;
持久磁盘上永远只有一个密文单包 `~/.okf-secret/vault.tar.gz.gpg`(gpg 对称 AES256,口令=密钥,
无托管、无后门;包名不含主题信息)。工具链(pi-llm-wiki/iwe)代码零改动——加密对文件系统层透明。

### 日常循环(SOP)

```bash
SV=tools/secret-vault/okf-secret-vault.sh

$SV init                 # 首次:建 tmpfs 工作区(含 inbox/)
$SV unseal               # 已有密文包 → 解密解包到内存
$SV run                  # 开会话:自动隔离会话产物 + MCP 指向本工作区
#   … 会话中:保密文档先拷进工作区 inbox/ 再 wiki_capture_source …
$SV seal                 # 封存:打包 → AES256 加密 → 原子替换 → 擦除内存工作区
```

- `run` 自动做四件事:会话转录/缓存隔离到工作区(CLAUDE_CONFIG_DIR + XDG_CACHE_HOME)、
  剥离遥测的会话 settings.json、禁用编辑快照、注入保密会话行为约束(不向工作区外写文件、
  内容不外发)并在启动时打印推理端地址供确认——**推理端必须是受控内网网关**;
- **输入纪律**:保密文档**先拷进工作区 `inbox/`(内存)再 capture**,绝不先落普通磁盘;
  capture 完成后清空 inbox(seal 时 inbox 非空会被拒绝,提醒你没处理完);
- **分段 seal**:每完成一段 ingest 就 seal 一次(seal 幂等,可重复执行)——崩溃/断电只丢
  内存中未封存的改动,已封存段落无损(**这就是保密库的"保存"**,不做另存明文备份);
- **保密库一律从源头重灌**(文档进 inbox 再建库),不做既有明文库的"洗白迁移"——SSD/journal
  使原地擦除不可保证;确需迁移时按降级手段处理,并如实声明历史残留(见工具 README)。

### 路径固定原则

工作区路径固定 `/dev/shm/okf-secret-vault`,不随会话变化——qmd 索引 manifest 记录绝对路径。
路径一旦变化(或从别处迁入),跑一次**无模型**词法重索引修复:

```
wiki_reindex { "components": ["lexical"] }     # 修复后 state: ready
```

### 封存态与消费

- 平时密文包在磁盘、工作区不存在——**任何人都查不到内容**(平台也查不到);
- 要用时:`unseal` + `serve`(只读 HTTP 服务,端口 8904,供平台/多机消费)或 `run`(本地隔离
  会话);用完 `stop` + `seal`;**服务在跑时 seal / unseal --force 会被拒绝**(先 stop,防抽走
  服务正在读的 vault);
- 保密库开给平台查的前提在**平台侧留痕**(会话落库/模型网关不受 okf-kb 控制):普通内网环境
  **不能开**;受控环境需平台侧出结论——完整分析见 `平台查询流程-HTTP形式.md` §4。
