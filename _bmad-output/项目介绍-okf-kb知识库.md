# okf-kb 知识库项目介绍

*2026-10-10(2026-10-14 修订:平台接入形态 stdio → HTTP;只读工具 4 → 5)*

## 一、项目概览与当前进度

本项目把存量文档编译成 OKF 格式的知识库,接入智能体平台供问答使用:文档先原样封存,再整理成相互链接的知识页,每条知识都能回溯到原始文档。

**当前进度:** 工具链(okf-kb)已封版(2026-09-24),自带运行时,可离线部署到内网;建库规范已定稿,完整流程经实测验证;第一个数据源 Confluence wiki 已完成,其余数据源后续按同一模式接入。

## 二、项目结构

**工具链(okf-kb 仓库):**

```
okf-kb/
├── tools/pi-llm-wiki/   # 写侧:capture(源包)、建页、lint 治理;词法检索(MCP server)
├── tools/iwe/           # 只读结构层:体系树/图查询/OKF 格式校验
├── tools/node24/        # 自带 node 运行时
├── docs/                # 建库指南 + OKF 规范与参考
└── raw-inbox/           # 原料入口
```

**知识库:** 每个数据源一个独立库,互不共享文件;库的内部结构见第四节。

**平台接入:** 每个库以只读方式接入智能体平台,绑定专属助手。

## 三、wiki 输出是怎么实现的

**1. capture——原文封存。** 每份原料经 `wiki_capture_source` 存为源包(`raw/sources/SRC-xxx/`):`extracted.md` 是原文,一个字不改、永久封存;`manifest.json` 登记来源。整理不满意可换更强的模型重跑,原料不丢。

**2. ingest——大模型读原文,建知识页。** 建库会话的模型通读原文,先搜后建(查重防重复页):

- 为每份源包建 **source 页**:摘要、要点、术语清单,页头(frontmatter)里指回原文;
- 用 `wiki_ensure_page` 建/更新 **concept 页**(概念)、**entity 页**(实体),正文互相链接并回源;
- 出现新体系时建 **synthesis 页**——枢纽页,用独占一行的链接把成员页挂进体系。

**3. 治理。** `wiki_lint` 查断链/孤儿,OKF 格式校验通过后 git 提交入库;顺带更新检索索引(只索引 wiki/ 层,原文不进索引——所以术语必须写进 source 页,否则搜不到)。

## 四、输出的 wiki 是什么结构

每个库以 `.llm-wiki/` 为根,分三个区:

```
.llm-wiki/
├── raw/                    # 原料:只增不改
│   └── sources/SRC-2026-09-23-001/
│       ├── extracted.md        # 原文(原样封存)
│       └── manifest.json       # 来源登记(哪来的、何时进的)
├── wiki/                   # 知识页:唯一事实源
│   ├── sources/                # source 页
│   ├── concepts/               # concept 页
│   ├── entities/               # entity 页
│   └── syntheses/              # synthesis 页(枢纽页)
└── meta/                   # 生成物:registry、检索索引等,可由 wiki 重建
```

**页与页的关系:**

- 回源:每个知识页正文写出处,如 `依据:[source](/sources/SRC-xxx.md)`——任取一条知识,都能沿"知识页 → source 页 → raw 原文"追溯回源头;
- 体系挂载:枢纽页里独占一行的链接表示体系归属,成员页行内回链枢纽;
- 一页被多少个枢纽收录,就在多少个体系里;文件只有一份。

## 五、存量、增量、全量更新

**存量——首次建库。** 源系统中已经积累的全部文档。首次建库把存量整体抽取进来:逐份封存为源包,再整理成知识页,完成与源系统存量的对齐。

**增量——日常更新。** 建库之后,源系统的新增与修改按增量方式进入知识库:

- 每个源有一个水位线(增量游标,记录"已处理到哪里"),按源系统的修改时间信号只取变化的条目;
- 每次捕获登记"源系统文档 key ↔ SRC 编号 ↔ 内容指纹"的映射(keymap):同一文档重捕时,内容未变则跳过;内容变了则新建源包,新 source 页注明取代旧 SRC,旧页置 deprecated(停用);
- 顺序固定:捕获全部成功 → 推进水位线 → 建图。失败不推进水位线,重跑结果一致。

**全量——周期对账。** 水位线会有遗漏(源系统索引有延迟、删除不留痕迹、改名与移动不一定反映在修改时间上),因此按源周期性做全量对账:

- 重扫不重捕:忽略水位线扫描整个源,内容未变的条目只比对、不重新捕获,不会产生重复源包;
- 找出漏捕、删除、改名与移动的条目,产出清单并告警;
- 一期不自动删页:人工确认后,对应的知识页才置为 deprecated(停用)。

## 六、怎么应用输出的 wiki

知识库不直接给人翻文件——它以**只读 MCP 工具**的形式接入智能体平台,由绑定该库的专属助手在对话中检索、阅读、作答。接入是纯配置,平台代码零改动。

### 6.1 接入:三步

**1. 在 okf-kb 服务器上起只读服务。** MCP 走 **HTTP 模式**:每库一个常驻只读服务(`LLM_WIKI_HTTP=1` + `LLM_WIKI_READ_ONLY=1`,端口 8901-8904),**库文件不出 okf-kb 服务器**;平台侧零副本——没有挂载、不需要与平台同机、不需要改容器编排。保密库另走封存循环:平时密文封存、服务不跑;要用先解封(内存盘)再 `okf-secret-vault.sh serve` 起 8904,用完 `stop` 再封存。

**2. 注册 MCP server(每库一条 url)。** 平台后台新增 **url 型**记录:填服务地址(`http://<okf-kb 服务器>:端口/mcp`);超时显式配置(不写会静默回落到 300 秒);库根路径与只读开关全部在**服务端**配死,平台侧不传任何 env。

**3. 建专属助手并默认绑定。** 每库一个专属 agent,默认绑定对应的 server;用户在对话里直接提问。跨源问答 = 同一助手同时绑定多个库(各库各一条 server,页面互不共享)。注意:平台进程加/删 server 后需**重启生效**。

**只读是两道防线:** 服务端只读模式(仅注册 5 个只读工具,写侧工具**物理不注册**;`WIKI_ROOT`=`WIKI_HOME` 配死,个人库不参与召回)· **网络面收敛**(HTTP 无内置认证——防火墙只放行平台服务器,或加认证反代)。每库接入后跑一次验证:服务可达 + 调库体检返回本库,且工具列表**恰为 5 个**(多于 5 说明只读模式没生效,必须停服务排查)。注意三点:①助手绑定只决定"默认可用",不是访问控制;②5 个工具里的 `wiki_lint` **带写能力**(调用会写库内报告/差距记录,`auto_fix=true` 时还能建占位页)——不接受任何写行为的场景须把它从补丁白名单裁掉(裁掉即 4 个);③保密库的"不开服务即不可达"靠停服务实现。

### 6.2 助手拿到什么:5 个只读工具

| 工具 | 干什么 | 什么时候用 | 关键返回 |
|---|---|---|---|
| `wiki_recall` | 主检索:按主题打分召回(CJK 词法) | 不知道确切名字时 | 页列表:id、标题、类型、预览(约 200 字符)、得分 |
| `wiki_search` | 精确检索:查登记表快速定位 | 知道确切名字/术语时 | 页列表:id、标题、类型 |
| `wiki_read` | 读全文(frontmatter + 正文) | 拿到页 id 之后 | 整页内容;长页自动分页(默认一窗 6000 字符,带上限 20000 与 `has_more`/续读 `offset`) |
| `wiki_status` | 库体检:页数/类型分布/孤儿/健康 | 自检与排障 | `{totalPages, byType, orphans, health}` |
| `wiki_lint` | 健康深查:孤儿/断链/矛盾/缺口,并写报告 | 定期巡检 | 检查摘要 + 库内报告路径;**带写能力,见 6.1** |

召回与检索**分工唯一、不可互替**:不知道确切名字用召回,知道用检索。两者都只返回"索引卡",读到内容要靠 `wiki_read`——一次典型提问两步完成:**召回 + 读全文**。

### 6.3 一次问答的调用流程

1. 用户在绑定了该库专属助手的会话里,**用自己的话**提问(现象、事项、术语都行);
2. 助手调 `wiki_recall(query)` 召回 → 拿到候选页列表(id + 类型 + 预览 + 得分);
3. 挑最相关的页调 `wiki_read(page_id)` 读全文(长页自动分页续读,连续读可拼出完整正文);
4. 知识页不够深时,沿页内"依据"链接读 **source 页**——该来源的摘要、要点、术语,以及来源系统登记(哪条、谁提的、何时进的);
5. 综合页面内容作答,答案附来源页,可核对回源系统里的原始条目。

浅问题停在知识页(第 2–3 步);深问题到 source 页为止。**raw 原文不在消费面**:原文永久封存在库内(供重跑与回溯),消费助手读不到——也不需要,source 页已承载消费所需的来源信息。没找到时,助手答"没有找到"而不是用模型自身记忆作答——让人能区分"库里没有"与"库坏了"。

例:值班人问「半年前那类超时告警怎么处理的」→ 召回命中当年处置沉淀出的知识页 → 读全文 → 沿来源读到对应 source 页(带工单号与时间)→ 拿着带来源的答案直接处置。

## 七、一句话总结

一份原文进库,封存为源包(`raw/`),整理成 source 页与 concept 页(`wiki/`),检索索引随之更新(`meta/`);提问时从召回知识页开始,需要多深就沿"知识页 → source 页"读到多深——原文封存在库里,供建库侧重跑与回溯。
