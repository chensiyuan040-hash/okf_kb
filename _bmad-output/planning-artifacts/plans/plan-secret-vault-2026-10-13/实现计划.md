# 实现计划:保密知识库(secret-vault)

日期: 2026-10-13 · 状态: 阶段 0 已完成(PoC 实测通过), 阶段 1 起待排期
相关产物: `tools/secret-vault/{okf-secret-vault.sh, README.md}`

---

## 一、问题背景与原因脉络

### 1.1 需求触发

okf-kb 的定位是内网离线知识库工具链:把散乱知识按 OKF 规范构建成图,核心架构「一源两读者」
(pi-llm-wiki 管写侧与生命周期,iwe 管只读结构层)。建库指南(2026-10-10 定稿)已覆盖常规资料的
capture→ingest→synthesize 全流程。

新需求:**保密文档(涉密/敏感资料)也要建成 wiki 知识库**。但保密管理规范要求这类内容
**不得以明文形式保存在文件系统**。于是两条约束正面相撞:

- pi-llm-wiki 的设计前提是「一批 markdown 文件是唯一事实源」—— 明文文件即数据库;
- 保密要求:持久磁盘上不得出现明文。

### 1.2 原因脉络:为什么不能简单"加密 vault 目录"

沿冲突往下推,四层原因逐一浮现(均为 2026-10-13 实测):

**第一层:vault 内就有 3 份明文副本。** pi-llm-wiki 的 QMD 检索索引不是引用,是复制:
`wiki/**/*.md` 知识页之外,`meta/qmd/documents/**` 是同内容的全文镜像,`index.sqlite` 的
`content` + `documents_fts*` 表是第三份全文。只加密 `wiki/` 目录没有意义。

**第二层:明文读写是整条链路的工作方式。** MCP server 的 15 个工具、检索、lint 全部实时读写文件
(扩展层实测 58 处 readFileSync/writeFileSync,recall 直接读 `wiki/*.md`),没有任何加密接口。
在存储层做加密 = 重写上游 pi-llm-wiki,不可行也不应为 —— 上游是外部维护的代码。

**第三层:vault 之外还有泄漏面。** 建库会话本身会到处留痕:
- Claude Code 会话转录 `~/.claude/projects/*.jsonl` **原样记录 MCP 返回的 wiki 全文**
  (实测某会话 40 处 tool_result 携带全文);
- `~/.claude/file-history/`(编辑前快照,本机实测 6.5M)、`paste-cache/`(粘贴缓存)、
  `shell-snapshots/`、`history.jsonl` 同理;
- 输入文档本身(docx/pdf)落到磁盘的任何一刻即已违反约束。

**第四层:约束的正确表述是全局不变量。** 上述三层说明要防的不是"某个目录",而是
**「明文不得触碰持久磁盘」** —— 必须按不变量设计,而不是按某个文件路径设计。

### 1.3 方案推导(排除法)

| 候选 | 致命伤 | 判定 |
|------|--------|------|
| 加密 vault 目录(单点) | 第一层:3 份副本,加密一份无用 | ✗ |
| 改造 pi-llm-wiki 存储层 | 等于重写上游,且破坏一源两读者架构 | ✗ |
| 挂载式加密卷(LUKS/gocryptfs/eCryptfs) | 挂载期间明文回到文件系统可见;内网离线装组件麻烦;依赖"记得卸载"的操作纪律 | 降级备选 |
| **tmpfs 工作区 + gpg 单包密文** | 明文生命周期限制在内存;gpg+tar 零新依赖(内网标配);单文件密文顺带解决备份/传输 | ✓ 选定 |

选定方案的两个可行性依据:
1. **工具链零改动**:MCP server 经 cwd/`WIKI_ROOT` 解析 vault(实测 `WIKI_ROOT` 语义=vault 根,
   指向 tmpfs 即生效),加密对文件系统层完全透明;
2. **Claude 自身产物可同址隔离**:实测 `CLAUDE_CONFIG_DIR` 重定位后,会话转录落回 tmpfs 工作区,
   原 `~/.claude/` 零写入、无双写、认证不受影响。

## 二、计划描述

### 2.1 目标与不变量

**目标**:把 secret-vault 从 PoC 做成 okf-kb 发布包内的正式功能 —— 一个未经培训的使用者
仅凭文档,就能安全地完成「保密文档 → wiki 库 → 封存 → 再开启检索」的完整循环。

**不变量(设计基准,所有阶段不得违反)**:
- I1 明文只存活于 tmpfs,seal 后内存/磁盘均无残留;
- I2 工作区路径固定(`/dev/shm/okf-secret-vault`),路径变更后必须 lexical reindex;
- I3 保密库一律从源头重灌(inbox 落料),不做既有明文库的"洗白迁移";
- I4 会话隔离(CLAUDE_CONFIG_DIR + --mcp-config)默认开启;
- I5 工具链(pi-llm-wiki/iwe)代码零改动。

### 2.3 关键设计决策(已定,避免返工)

| # | 决策 | 理由 |
|---|------|------|
| D1 | 工作区路径固定,不随会话变化 | qmd manifest 存绝对路径,变则须 reindex(I2) |
| D2 | 保密库从源头重灌,不迁移既有明文库 | SSD/journal 使原地擦除不可保证,迁移只作降级手段并如实声明残留 |
| D3 | 默认对称加密(口令=密钥),无密钥托管 | 单人单机场景最简单;多接收者留阶段 4 |
| D4 | 密文包默认 `~/.okf-secret/vault.tar.gz.gpg`,权限 600 | home 下便于备份;名称不含主题信息(元隐私) |
| D5 | MCP 接入用显式 `--mcp-config` | 隔离后的配置目录无用户级 MCP 配置,显式最稳 |

### 2.4 风险与缓解

| 风险 | 缓解 |
|------|------|
| 用户忘记 seal,明文长期驻留内存 | run 退出提示 + status 显著标记"明文态" + 可加 shell 提示(阶段 4) |
| 崩溃丢失未 seal 的改动 | 分段 seal 纪律(每完成一段 ingest 即 seal);seal 幂等可重复执行 |
| 运行期同机进程读内存 | 无解,已在威胁模型边界声明(任何方案皆然) |
| **会话期系统休眠(hibernate)**: 内存整体写入磁盘, tmpfs 明文全部落盘 | 主风险之一;对策: 会话期禁用 hibernate(`systemctl mask hibernate.target suspend-then-hibernate.target`), suspend-to-RAM 不禁 |
| **tmpfs 页可被 swap 换出**: 内存压力下 /dev/shm 的明文页写入 swap 设备 | 阶段 4.1: 会话模式 swapoff, 或 root 自挂 ramfs(不可换出, 需容量自律防 OOM), 或 zram |
| **core dump**: 进程崩溃时内存写入磁盘 | `ulimit -c 0` 进 run 环境; 系统级 core_pattern 检查 |
| **遥测网络流**: 本机 `OTEL_LOG_USER_PROMPTS=1` 会把 prompt 全文发往 collector | run 已剥离遥测(会话 settings.json); 阶段 2 增部署审计项: collector 侧政策与留存 |
| **推理端网络流**: 内容以明文到达 `ANTHROPIC_BASE_URL` | 部署层保证内网受控模型网关; run 启动打印端点供人工确认; 公网端点(如现开发机)禁止用于保密会话 |
| 口令丢失 = 数据不可恢复 | 文档显著声明,无后门;口令强度提示 |
