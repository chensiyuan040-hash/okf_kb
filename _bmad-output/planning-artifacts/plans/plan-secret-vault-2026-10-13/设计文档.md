# 保密知识库(secret-vault)设计文档

> 日期:2026-10-14 · 读者:架构组、安全评审、运维
> 配套:`tools/secret-vault/`(工具与操作手册)、同目录 `实现计划.md`(工程计划与排期)、
> `tools/secret-vault/README.md`(泄漏面盘点原始记录)
> 一句话:**保密文档建成的 wiki 库,持久磁盘上任何时刻都不存在明文**——明文只活在内存盘
> (tmpfs),磁盘上只有一个加密包,用完封存。

---

## 一、问题:两条约束正面相撞

- **保密管理规范**:保密文档不得以明文形式保存在文件系统(磁盘、备份、日志都算);
- **建库工具的工作方式**:pi-llm-wiki 的设计前提是「一批 markdown 明文文件就是数据库」——
  所有工具实时读写明文文件(实测 58 处 readFileSync/writeFileSync,检索直接读 `wiki/*.md`),
  没有任何加密接口。

排除法选方案:

| 候选方案 | 为什么不行 |
|---|---|
| 只加密 vault 目录(单点) | vault 内同一份内容有 **3 份明文副本**(知识页、检索镜像、索引库全文,见 §二),加密一份没用 |
| 改造建库工具的存储层 | 等于重写上游(外部维护的代码),不可行也不应为 |
| 挂载式加密卷(LUKS / gocryptfs) | 挂载期间明文照样在文件系统里可见;"忘记卸载"就长期明文;内网离线装组件麻烦 |
| **内存盘工作区 + gpg 单包密文** | ✓ 选定:明文生命周期锁死在内存;gpg + tar 系统自带、零新依赖;单文件密文顺带解决备份/带出 |

关键认识:**要保的不是"某个目录",而是"明文不得触碰持久磁盘"这条线**——按整条链路
(输入 → 建库 → 检索 → 会话 → 封存)设计,而不是按某个文件路径设计。

## 二、明文会落在哪(泄漏面盘点)

设计的根据是下面这张表(2026-10-13 逐项实测):

| # | 落点 | 内容 | 结论 |
|---|------|------|------|
| 1 | vault 的 `.llm-wiki/raw/sources/SRC-*/` | 原始文档 + 规范化全文 | 明文 |
| 2 | vault 的 `wiki/**/*.md` | 知识页 | 明文 |
| 3 | `.llm-wiki/meta/qmd/documents/**` | 检索索引的**全文镜像**(与知识页同内容) | 明文,第 2 份副本 |
| 4 | `.llm-wiki/meta/qmd/current/index.sqlite` | 全文表 + 全文索引 | 明文,第 3 份副本 |
| 5 | `meta/registry.json` 等 | 标题、来源、目录结构 | 明文 |
| 6 | `~/.claude/projects/*.jsonl` | 会话转录(**原样记录 wiki 全文**,grep 实测命中) | 明文,最大的隐形泄漏 |
| 7 | `~/.cache/claude-cli-nodejs/.../mcp-logs-*` | MCP 连接调试日志 | 实测只含连接信息;已随会话隔离改道 |
| 8 | OTel 遥测(网络流) | prompt 全文经 OTLP 发往 collector(本机 `172.16.52.100:4317`) | 本地隔离防不住,须剥离 |
| 9 | 推理端(网络流) | 内容以明文到达模型服务 | 必须受控内网模型网关 |
| 10 | swap / 休眠 / core dump | 内存页落盘路径 | 可配置消除(阶段 4) |

三条结论:
1. **vault 内一份内容 3 份明文副本** → 单点加密无意义;
2. **会话转录把全文写进 `~/.claude/`**(实测某会话 40 处 tool_result 携带全文)→
   即使 vault 全加密,建库过程照样泄漏 → 会话面必须一起隔离;
3. **第 8/9 条是网络流** → 本地手段的边界之外,只能靠部署控制(隔离遥测 + 内网模型网关)。

## 三、方案总览

```
持久态(磁盘唯一形态)            工作态(内存, tmpfs)
~/.okf-secret/                  /dev/shm/okf-secret-vault/(路径固定)
  vault.tar.gz.gpg   ⇄⇄⇄⇄        ├── .llm-wiki/     ← 建库工具在这里实时读写
  (AES256 对称加密)   unseal       ├── .session/      ← 会话产物(转录等)隔离目录
                     seal →       ├── inbox/         ← 保密输入文档暂存
                                  └── …服务 pid / 日志(随 seal 消失)
```

- **不变量**:保密文档从进入系统(capture)到建库、检索、会话结束,明文只存活于 tmpfs;
  磁盘上永远只有密文单包;seal 后工作区整个删除——内存文件无磁盘残留。
- 加密用 **gpg 对称(AES256-SHA512)**:口令即密钥,无托管、无后门;包名 `vault.tar.gz.gpg`
  不含主题信息(元隐私);文件权限 600。
- 与挂载式加密卷的核心差别:**tmpfs 的明文从不落盘**,会话结束对象直接消失,
  不依赖"记得卸载"这种操作纪律。
- 备份/带出 = 拷一个加密文件;将来多人共享可扩展 gpg 多接收者(阶段 4.2)。
- 对建库工具**透明**:工作区路径固定,`WIKI_ROOT` 指向 tmpfs 即生效,工具链零改动(实测通过)。

## 四、设计不变量(所有实现不得违反)

| # | 不变量 |
|---|--------|
| I1 | 明文只存活于 tmpfs 工作区;seal 后内存/磁盘均无残留 |
| I2 | 工作区路径固定(`/dev/shm/okf-secret-vault`);路径一旦变化,须跑一次词法重索引修复(qmd 记录的是绝对路径) |
| I3 | 保密库一律**从源头重灌**(文档先拷进 inbox 再 capture),不做既有明文库的"洗白迁移"(SSD/journal 使原地擦除不可保证) |
| I4 | 建库会话隔离默认开启(会话产物/缓存全部改道 tmpfs) |
| I5 | 建库工具链(pi-llm-wiki / iwe)代码零改动——加密对文件系统层透明 |
| I6 | 只读服务在跑时,`seal` / `unseal --force` 被拒绝——先 `stop` 停服务再封存(防止抽走服务正在读的 vault) |

## 五、各环节设计

### 5.1 存储与生命周期(init / unseal / seal / destroy)

| 动作 | 做什么 | 设计要点 |
|---|---|---|
| `init` | 建 tmpfs 工作区 | 固定路径;建 `inbox/` |
| `unseal` | 密文包 → 解密解包到内存 | 口令输入不回显;`--force` 覆盖已有工作区(服务在跑时被拒) |
| `seal` | 打包 → AES256 加密 → **原子替换**密文包 → 擦除工作区 | 幂等,可重复执行——推荐纪律:每完成一段 ingest 即 seal,防崩溃丢改动 |
| `run` | unseal(如需)+ 以隔离会话启动 claude | 见 5.2 |
| `serve` / `stop` | 起 / 停只读 HTTP 服务 | 见 5.3 |
| `status` | 显示状态 | 明文态/封存态/服务状态显著标记 |
| `destroy` | 销毁 | 自动先停服务 |

### 5.2 建库会话隔离(run)——防第 6/7 号落点

实测确认:Claude Code 会话转录(jsonl)会**原样记录 MCP 返回的 wiki 全文**;`~/.claude/`
的泄漏面还不止转录,还有 `file-history/`(编辑快照)、`paste-cache/`、`history.jsonl`、
`shell-snapshots/`。run 做四件事:

1. **`CLAUDE_CONFIG_DIR` → 工作区 `.session/`(tmpfs)**:转录等会话产物全部落回内存盘
   (实测:转录落在 `.session/projects/...`,原 `~/.claude/` 零写入、无双写,认证不受影响);
2. **`XDG_CACHE_HOME` → 工作区 `.cache/`**:顺带带走 MCP 日志、错误缓存
   (`~/.cache/claude-cli-nodejs` **不受** CLAUDE_CONFIG_DIR 控制,必须单独改道);
3. **会话 settings.json 生成**:白名单继承认证/模型配置,剔除全部 `OTEL_*` 并显式
   `CLAUDE_CODE_ENABLE_TELEMETRY=0`,同时禁编辑快照(`fileCheckpointingEnabled: false`)——
   **因为 settings.json 的 env 块优先于 shell 环境,光在 shell 里 unset 遥测变量无效**(实测教训);
4. **`--mcp-config` 显式指向工作区**:`WIKI_ROOT` 与 `WIKI_HOME` 同指工作区——后者关闭
   "个人库合并"(隔离后的默认个人库是宿主 `~/.llm-wiki`,不设时其内容会混入检索结果,见 5.3 实测)。

启动时打印 `ANTHROPIC_BASE_URL` 供人工确认推理端受控(第 9 号落点,脚本只能提示)。

### 5.3 平台/多机消费面(serve / stop)——2026-10-14 增

保密库也要能被平台查,形态与普通库一致:**只读 HTTP 常驻服务**(端口 8904)。

- 服务端**只读配死**(`LLM_WIKI_READ_ONLY=1`):写侧工具物理不注册(工具面恰 5 个);
  已知例外 `wiki_lint` 带回写行为,但它写的全部是**工作区内**的文件(报告/元数据/stub 页),
  seal 时一并封存——不产生磁盘明文;
- **`WIKI_HOME` 同指工作区是必设项**(脚本已内置):不设时 recall 会把宿主 `~/.llm-wiki`
  的内容合并返回给查询方;只读补丁不管合并,该变量是唯一防线(对照实验实锤);
- **HTTP 面无内置认证**:监听从 `127.0.0.1` 放开时脚本会提示——用防火墙只放行消费方,
  或前置认证反代;
- **封存/解封循环**:平时密文包在磁盘、服务不跑(平台天然查不到) → 要用时 `unseal` 到内存
  + `serve` → 用完 `stop` + `seal`;
- `seal` 与 `unseal --force` 在服务在跑时被拒绝(I6);`destroy` 自动先停服务;
  pid/日志都在工作区,随 seal 消失。

**保密库能不能开给平台**:取决于平台侧的留痕(会话消息与工具返回内容落平台 PG 数据库、
模型网关推理)——普通内网环境**不能**;整体满足保密要求的受控环境可以,需平台侧出结论。
完整分析见 `architecture-okf-kb-2026-10-10/平台查询流程-HTTP形式.md` §4。

### 5.4 输入纪律(inbox)

保密文档**先拷进工作区 `inbox/`(tmpfs)再 capture**,绝不先落普通磁盘;这是 I3 的操作面。
capture 完成后 inbox 清空。

## 六、威胁模型边界

| 防得住 | 防不住 |
|---|---|
| 磁盘/机器被拿走、挂载盘被单独读取(静止态全密文) | 运行期间同机 root/进程读内存(tmpfs 明文可见,任何方案皆然) |
| 磁盘上残留明文副本、日志、会话转录(配合 run 隔离) | swap 换出、休眠(hibernate)把内存页写盘——阶段 4.1 提供 swapoff / ramfs 选项 |
| 输入文档在进入本工作流后的全链路 | 截屏 / 内存转储 / 硬件后门 |
| | 输入文档在进入本工作流**之前**的历史落盘残留 |
| | 网络流:遥测(已剥离)/ 推理端(须受控网关,部署层保证) |

密钥即口令:口令强度 = 密文强度;丢失口令 = 数据不可恢复,无后门。

## 八、关键设计决策(已定,避免返工)

| # | 决策 | 理由 |
|---|---|---|
| D1 | 工作区路径固定,不随会话变化 | qmd manifest 存绝对路径,变则须重索引(I2) |
| D2 | 保密库从源头重灌,不迁移既有明文库 | SSD/journal 使原地擦除不可保证;迁移只作降级手段并如实声明残留 |
| D3 | 默认对称加密(口令=密钥),无密钥托管 | 单人单机场景最简单;多接收者留阶段 4.2 |
| D4 | 密文包默认 `~/.okf-secret/vault.tar.gz.gpg`,权限 600 | home 下便于备份;名称不含主题信息(元隐私) |
| D5 | MCP 接入用显式 `--mcp-config` | 隔离后的配置目录没有用户级 MCP 配置,显式最稳 |
