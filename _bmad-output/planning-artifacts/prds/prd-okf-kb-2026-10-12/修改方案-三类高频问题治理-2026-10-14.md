## 0. 先讲清楚:十个问题收敛成三条线

逐条追踪根因后,三类问题其实只有三条病根,方案按三条线组织:

**病根一:采集和整理之间没有"完成"的定义,也没有机制检查"完成"。**
证据:采集工具写入的页面停在 `status: skeleton`、正文全是 `[LLM: …]` 占位符(问题 8);不会自动建链接所以是孤儿(问题 9);这个 `skeleton` 值不在库校验规范的状态词表里,所以校验必然报错(问题 17);体检工具发现了孤儿只报数量、不报名字,没有清单就没有行动(问题 16)。
→ **治理线 A(写侧闭环)**:给"整理完成"一个客观定义,给"没完成"一个卡口和一个工作清单。

**病根二:结构的正确性没有校验层,写错了装作没事。**
证据:体系页成员写成列表格式,层级当场塌平,退出码 0、零警告(问题 15);新旧替代关系写没写、写对不对,系统从不检查也不提示(问题 6);文件被手动编辑,内容生效但日志里什么都没有(问题 10)。
→ **治理线 B(发现侧补全)**:给每类"静默失效"配一个会响的警报。

**病根三:消费端拿到的信号不足,防误导全靠 AI 自觉。**
证据:旧版文档排在前面、废弃/过期标注不影响排序只是"文本"(问题 1/2/3);骨架页能被检索到(问题 8 的消费面);个人库条目混进结果,ID 风格和本库一模一样(问题 14)。
→ **治理线 C(消费侧硬信号)**:把提示从"正文里的一句话"升级为"检索结果自带的字段"。

## 1. 治理线 A:写侧闭环(治问题 8/9/17)

### 动作一:库状态检查工具 `vault-health`【本机产出】

**是什么**:一个独立脚本(`tools/okf-tidy/vault-health.mjs`),扫描 wiki 目录,回答一个此前没有工具回答的问题——**"这个库里,有多少页还没整理完?多少页挂空了?"**

**检查项(每条检查都对应一个已验证的问题)**:

1. **未整理页** —— 对每页读 frontmatter 和正文,凡是满足下列任一条件的就是"未整理":
   - `status: skeleton`(采集工具写的原始状态;依据:source-packet.ts:328 采集时写入)
   - 正文仍含 `[LLM:` 占位符(防止有人改了 status 却忘了删占位符——半整理)
   输出:未整理页完整清单(路径 + 命中原因 + 占位符残留条数)。
   *对应问题 8——"整理完成"第一次有了客观定义;也是 17 的整理清单来源。*

2. **体系页塌平** —— 对每个体系页合成页做两件事:
   - 扫正文,找"疑似成员但写法错误"的行:列表格式的页面链接(正则匹配 `^\s*[-*]\s*\[.+\]\(.+\)`,同时匹配带 `.md` 和不带 `.md` 两种链接形态——复核报告实测两种写法都存在);
   - 用 `iwe find --filter '{ $includedBy: { match: { $key: syntheses/<页名> } } }'` 查实际被认定为子成员的数量;
   - 对比:正文疑似成员数 > 实际成员数 → **塌平报警**(列出疑似成员行号);两者一致但疑似成员行存在 → 提示核对。
   降级:环境无 `iwe` 命令时,退化为"疑似成员行存在即提示"。
   *对应问题 15——把"零提示"变成"体检时必响"。*

3. **替代关系一致性** —— 扫全库 frontmatter:
   - 有 `superseded_by` 但 `status` 不是 `deprecated` → 报警(替代标注不完整);
   - 有 `supersedes` 的新页自身 `status` 不是 `stable`/`draft` → 提示;
   - `stale_after` 已过期但 `status` 仍为 `stable` → 提示(该走替代/复审了)。
   *对应问题 6/1/2/3 的"维护面"——替代关系的三件套写法有错,这里会响。*

4. **疑似版本对(警告级)** —— 标题规范化(去空格、去日期/版本数字)后相同或前缀包含、且两页均无 `supersedes/superseded_by` 标注、且均 `status: stable` → 提示"疑似新旧两版并存,请人工确认替代关系"。
   *对应问题 6 的"发现面"——第一次替代发生前,这个检查就是窗口期的哨兵。误报可接受(警告级,人工核对)。*

**输出形态**:
- 人类可读的 markdown 报告(默认打印,`--out <file>` 可落盘);
- `--gate` 模式:检查项 1(未整理)与 2(塌平)为**阻断级**,非零即退出码 1;其余为警告级只报告不阻断;
- `--snapshot <file>` 模式:把每个体系页的实际成员列表存成基线文件(见动作四的回归机制)。

**验收**:在克隆库构造三种场景(未整理页、塌平页、带标注的替代对)全部被报出;干净库退出码 0。

### 动作二:批次门禁(治 17 的口径 + 8/9 的卡口)【本机产出脚本,内网接入流程】

**门禁脚本**(`tools/okf-tidy/gate.sh`)在批次提交前跑两条:

1. `iwe schema validate` —— 结构合规(现有工具,用它本身);
2. `node vault-health.mjs --gate` —— 内容整洁(未整理=0、无新塌平)。

两条都过,退出码 0,批次放行;否则打印待办清单,退出码非零,不放行。

**问题 17 的口径决定——为什么不改校验规范**:

`iwe schema validate` 报的 "status: skeleton is not one of draft, stable or deprecated" 看似"工具自产自验不过",但我们**明确不改**(不往 schema 词表里加 skeleton),理由:

1. `skeleton` 是摄入机制的开关,不是可自由改的文案——摄入工具用"status 是不是 skeleton"判断"这份资料来源处理没处理过"(tools.ts:339),改掉会破坏跳过机制;
2. schema 报错**自带清单**(iwe 的校验会指名道姓输出哪个文档、哪个字段、错在哪一行,官方文档原话 "names the exact document, field, and rule")——这正是"待整理清单",比补充说明还好用;
3. OKF 规范的状态词表是 draft/stable/deprecated,对齐上游规范不如让**库运营层**承担"未整理可见":门禁脚本把 validate 的报错直接翻译成"以下页面未整理,请整理后重新提交"。

所以问题 17 的解决不是"修工具",是**改变对报错的解释并对接流程**:validate 报错 = 待整理清单 = 批次不放行的原因。这条口径写进操作手册(动作十)。

**验收**:克隆库放一个未整理页 → 门禁退出码 1,输出整理清单;清零后 → 退出码 0。内网接上批次流程后,任一未整理页无法过闸。

## 2. 治理线 B:发现侧补全(治问题 16/15/6/10)

### 动作三:lint 明细化补丁【bundle 补丁,本机产出】

**改哪里**:`tools/pi-llm-wiki/mcp-server.mjs` 的 `runWikiLint`(函数约在 236261 行起,返回摘要字符串以 `🧹 **LLM Wiki lint complete**` 开头,约 236409 行)。与现有 flags 补丁同流程管理,写进 CHANGELOG。

**改什么(三处,全部是"把已经算出来的信息显示出来",不新增计算逻辑)**:

1. 摘要里补明细:目前只打印 `- Orphans: 3`,而孤儿**名字本来就已经算出来了**(代码里 `findings` 数组含 `Orphan: <页ID> has no inbound links` 逐条) —— 摘要段改为:计数行之后跟 findings 前 20 条(超出写"等 N 项"),孤儿、缺失页、矛盾标注三类都列名;
2. 新增"未整理"计数行:`- Unfiled: <N>`(status 为 skeleton 或正文含 `[LLM:` 的页数,页对象已有 frontmatter 可读),并在 findings 里逐条列出——消费侧在会话里跑一次 lint 就同时拿到整理清单;
3. 报告文件不再只在 `--fix` 时落盘:非 autoFix 也写 `outputs/lint-<date>.md`(现在非 autoFix 时明细只存在于内存,报告文件根本不生成——这是"只报数量"的实际原因)。

**验收**:克隆库造 2 个孤儿 + 1 个未整理页 → 会话内跑 `wiki_lint` 返回的文本直接含三个页名;与基线对比,lint 的计数与事件记录不变。

### 动作四:体系页塌平检查 + 树基线【并入动作一 + 基线存档】

检查本体在动作一的检查项 2。这里补**回归机制**:

- 修复完整体系页之后(见第四节),立即用 `vault-health --snapshot baselines/tree-baseline-<日期>.txt` 存一份"每个体系页实际成员"的基线;
- 此后任何人跑 vault-health,除实时检查外同时 diff 基线,成员数变化即列出新旧差异。
- 效果:塌平不仅"体检时会响",而且"和上次比哪里变了"一目了然——修复不再依赖人的记忆。

**同时修文档**:建库指南补"三种写法对照"小表(裸链接独占一行 = 成员;`- [ ]` 列表 = 塌平;行内链接 = 普通引用),附修好的体系页做范例;依据是 iwe 官方文档原话 "An inclusion link is a markdown link placed on its own line"(docs/iwe/inclusion-links.md)。

### 动作五:替代关系一致性检查【并入动作一,检查项 3/4】

见动作一。首次跑真实库时把输出的"疑似版本对"清单交给维护者逐对确认——确认后的结果就是第一批正确的替代标注(问题 6 从"等人记得写"变成"体检推着写")。

### 动作六:编辑留痕钩子【本机产出,内网可选装】

**现状**:直接编辑文件,内容在重建后生效,但事件日志没有记录(问题 10;复核实测:改内容、重建、检索命中,日志行数一行不变)。已定对策是"编辑走受控路径、台账靠 git"(手册三条之一),本动作把"靠 git"从约定变成机制:

- `tools/okf-tidy/install-hooks.sh`:在 wiki 的 git 仓库安装 `post-commit` 钩子——每次提交后把(提交哈希、时间、变更文件列表)追加到 `.llm-wiki/meta/edits.log`。
- 效果:此后"谁、何时、改了哪些页"在库内即可查(与 git 双记录,但查询不需要 git 知识);hook 缺失时行为不变(纯可选增强)。
- 前置:确认内网 wiki 目录已纳入 git(P0-1 的修复流程本来就要求 git commit 留痕,说明 git 已具备)。

**验收**:改一页、提交 → edits.log 出现一行含该页路径的记录;仓库无 git 时脚本给出说明并跳过。

## 3. 治理线 C:消费侧硬信号(治问题 1/2/3/8 消费面、14)

### 动作七:flags 补丁扩展 + 内网部署【bundle 补丁,本机产出 → 内网部署】

**现状**:三 kind(superseded / deprecated / stale)的 flags 补丁本机已落盘(commit 6089269),内网 bundle 未替换。本动作 = 补一个 kind + 完成部署。

**扩展(一行级改动)**:`flagsOf()`(mcp-server.mjs 约 236864 行)增加:

```
if (entry.status === "skeleton")
  flags.push({ kind: "skeleton", detail: "未整理页(正文为占位符),内容待合成" });
```

**为什么值得**:这直接堵住问题 8 的消费面——骨架页被检索到时,以前防误用靠消费协议"人工读 frontmatter 自觉判断",现在**结果条目自带 flags**;配合消费协议,弱模型也拿得住。且纯叠加,分数排序不变(与三 kind 同一实测口径)。

**部署(与已有部署动作合并,不重复)**:内网替换标准 bundle → 冒烟(克隆库构造 skeleton 页 + 旧页) → 三种生命周期 kind 与 skeleton kind 各可见 → 分数与基线逐位一致 → CHANGELOG 记录重打流程。

### 动作八:消费协议联动【更新已有卡片,一行】

`docs/消费协议卡片.md` 第 5 条(skeleton 页不当内容使用)补一句:flags 补丁部署后,skeleton 页在检索结果中以 `flags: [{kind: "skeleton"}]` 硬标记呈现,见到该标记必须停用该条并向用户报告。第 2 条的"flags 为部署后才存在"注记改为部署状态说明。**无其他改动**——旧版提示(1/2/3)与跨库过滤(14)的协议条款此前已备好。

### 动作九:多库治理(16 部署体检 + 两种情形决策)【内网,决策成本:低】

问题 14 发生在"消费机同时挂了个人知识库"的部署形态下,默认行为会混入 personal 条目(ID 与库内一致、带 `vaultLabel: "📚 personal"` 字段)。治理分两步:

1. **体检(5 分钟)**:在内网消费机检查 `~/.llm-wiki/` 是否存在且配置有效(`config.json`),以及用库会话的实际检索返回里是否出现 `vaultLabel` 字段。两者任一为否 → 问题不存在,本条关闭;
2. **若存在 → 二选一**:
   - **首选:消费机不挂个人库**——个人知识库是开发者环境产物,内网服务形态本就该是单库。清理个人库配置即彻底解决,零补丁。
   - 次选(仅当多库共存是刻意需求):评估在 bundle 里给 personal 条目把标签升格为醒目前缀的实现成本,再定是否做——**不在本方案承诺范围**,只是把口子留在这里,避免届时又从头分析一遍。

## 4. 内网就地执行(整合已有计划条目,不重复设计)

以下三项已有完整操作序列,本文只标注与本方案衔接的部分:

1. **10 个体系页修复**(已有 P0-1,含 sed 序列与 git 留痕要求)→ 修完紧接执行**动作四的基线存档**(一条命令);

**操作手册补充三条**(并入已有手册文档):

- 整理完成的定义:三件全清才算完成——去占位符、补链接(至少一条入/出链)、status 改 draft(vault-health 检查项 1 的判定口径,保持一致)。
