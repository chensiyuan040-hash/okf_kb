## 1. 愿景

团队的知识目前散落在四个互不相通的地方:Confluence 的博文、禅道的项目与缺陷记录、Nextcloud 网盘的文件、以及 BM 保密网络安全知识文档。这些知识对人有价值,但对**平台上的 agent 不可达**——agent 无法回答"我们上次这个故障是怎么处理的""这条安全要求出自哪份文档"。

okf-kb 知识库系统把四个源编译成四个**结构化的、可枚举体系的**知识库:不是把文件塞进检索索引,而是把原料编译成互相链接的知识页(概念页、实体页、体系枢纽页),并保证每一条知识都能回溯到它的原始出处。四个知识库各以一条只读 MCP server 接入 wa-platform,绑定到专属 agent,用户可以直接向 agent 提问并拿到带来源的答案。

**本项目的赌注**:知识库的价值上限取决于**编译质量**而非检索算法——先建成体系可枚举、来源可追溯的图,再谈检索。因此系统把工程重点放在"每一批都必须过质量门"和"失败必须可追溯、可重跑"上,而不是堆检索能力。检索先用词法方案上线,用可测量的召回基线决定是否值得引入向量。

## 2. 目标用户

### 2.1 待办任务(JTBD)

- **(问答者 / 功能)** 我要向绑定知识库的 agent 提问,并拿到一个能指出出处的答案,这样我不用自己去四个系统里翻。
- **(问答者 / 情感)** 我要**敢于**把这个答案转述给同事或用在方案里——因为我知道它来自某份具体文档而不是模型的记忆。
- **(问答者 / 情境)** 我可能问得很含糊(同一个事在不同系统叫法不同),希望知识库自己能把相关页找齐。
- **(运维 / 功能)** 我要在不盯着它的情况下知道流水线今天跑了没有、失败没有、库是空的还是坏的。
- **(运维 / 情境)** 出事时我要能重建现场:这批抓了什么、失败在哪一步、能不能原样重跑。
- **(知识人审 / 判断)** 我要用有限的时间抽查最可能出错的地方(机器综合出来的页),而不是逐页读。
- **(平台工程师 / 集成)** 我要以最小改动把四个库接上平台——不改平台代码,只在后台加配置。
- **(安全评审 / 合规)** 我要能说清楚保密内容进了哪里、以什么形态存在、谁能看到——并对已知的暴露面做出**明示的**风险接受,而不是假设它不存在。

### 2.2 非用户(v1 明确不服务)

- **平台外的用户**:v1 全部在内网,不对外提供服务。
- **想要"知识库写回源系统"的人**:知识库是单向只读采集,不回写 Confluence/禅道/网盘。
- **想要多库联合视图的人**:没有跨库统一图谱,跨源关联只能靠一个 agent 同时绑定多库。
- **想要语义(向量)检索的人**:v1 只做词法检索,见 §5。
- **想要按用户/按文件细粒度授权的人**:隔离是库级逻辑隔离,不是文件级强权限,见 §9.1。

### 2.3 关键用户旅程

*命名场景,保留具体细节——细节才是需求。*

*以下旅程由架构输入与运维常识推演 `[ASSUMPTION: UJ 人物与情节非真实用户访谈产出;若需求方有真实使用场景,以其为准替换]`。*

- **UJ-1. 平台用户小李在值班中查一条历史故障。**
  - **人物 + 情境:** 小李是平台运维值班人,凌晨收到一条告警,怀疑是半年前处理过的同类问题;他不记得当时写在哪。
  - **入口状态:** 已登录 wa-platform,在会话里打开绑定了禅道知识库的专属 agent。
  - **路径:** 他用自己的话描述现象提问 → agent 调用 `wiki_recall` 召回相关页 → 对最相关的页调用 `wiki_read` 读全文 → 把答案连同 source 页一起回给他。
  - **高潮:** 他拿到答案,并且答案里带着**源系统中的原始条目**(哪条 bug、谁提的、什么时候)——这让他敢直接按它去操作。
  - **收敛:** 他按答案处置完,顺手把这条知识记进值班记录;不需要打开禅道。
  - **边界情况:** 如果知识库里确实没有这个知识,agent 应当说"没有找到",而不是用模型自身记忆作答——他需要能区分"库里没有"和"库坏了"。

- **UJ-2. 运维陈工处理一次夜间批次失败。**
  - **人物 + 情境:** 陈工负责这套流水线,白天有别的活,希望只在真出事时被打扰。
  - **入口状态:** 早上看到 Mattermost 告警:某库某批次 failed,带门代码与计数(不含文档标题/路径/正文)。
  - **路径:** 他查该批次的**批次报告**拿到批次 ID、失败门项与涉及页面清单 → 打开该批次的**完整运行日志**定位到具体阶段与原因 → 判断是配置问题还是数据问题 → 修正后按批次重跑(水位线未推进,重跑幂等)。
  - **高潮:** 重跑成功,批次转绿,他能确认这次没有数据被漏掉(水位线推进的正确性可核对)。
  - **收敛:** 批次报告留档,后续审计能回答"那天发生了什么"。
  - **边界情况:** 如果他拿到锁失败提示(有人正在手工建库),正确处置是**等**,不是绕过——流水线会把它记为 `skipped_locked`,不算失败、不推水位线。

- **UJ-3. 平台工程师张工接入第一个知识库(P0 联调)。**
  - **人物 + 情境:** 张工属平台团队,只做**后台配置**,不碰平台代码。
  - **入口状态:** okf-kb 侧已给出 server 配置片段与配置值(url、timeout;贴即用)。
  - **路径:** 他在后台 `mcp_server_configs` 建 1 条 **url 型** server(填服务地址与超时)→ 起会话验证 `wiki_status` 返回本库 → 确认工具列表恰为 5 个 → 建一个专属 agent 默认绑定该 server。(2026-10-14:HTTP 形态——无 compose 挂载、无容器重建。)
  - **高潮:** 他在会话里问了一个只有该库能答的问题,拿到带来源的答案。
  - **收敛:** 他把这次验证的命令集(服务可达性 + 工具列表断言 + 冒烟)固化进部署文档,后面三个库照着做。
  - **边界情况:** 若工具列表多于 5 个,说明只读模式没生效——此时**必须停下并停掉服务**,因为它刚把写能力暴露给了消费 agent。

- **UJ-4. 知识人审王工抽查一批综合页。**
  - **人物 + 情境:** 王工懂业务,不懂流水线内部;每周花固定的一小段时间做质量抽查。
  - **入口状态:** 拿到该批次的**批次报告**,其中含本批综合页抽样清单。
  - **路径:** 他按清单打开页面 → 检查机器综合的内容是否忠实于来源、体系挂载是否合理 → 发现问题的页面打回,并记录问题类型。
  - **高潮:** 他发现问题**集中在少数几页**,而不是普遍性错误——这验证了机械质量门确实兜住了结构性问题,人审只需覆盖语义层。
  - **收敛:** 打回的问题进入下一批的修正范围。
  - **边界情况:** ①清单为空(本批无新建页)——报告须显式标注"本批无人审样本",**不能读作"已审"**;②同一页连续两批被打回——说明模型的系统性偏差,须触发建图提示词复查而非继续逐批修;③清单里出现未挂载页——说明门 3 放行有误,须回查门本身(这是**门失效信号**,不是数据问题)。

## 3. 术语表

*下游文档与工作流必须逐字使用这些术语;在本文任何位置引入同义词都属违规。*

- **vault** — 一个知识库的完整目录,内含原料区、知识页区与生成物区。四个源对应四个 vault,互不共享页面文件。同义表述"库"在本文中即指 vault。
- **SRC(源包)** — 一次原料捕获的不可变副本,含该条原料的提取文本、出处清单与附件。
- **原料(raw)** — vault 内只增不改的原始条目集合;所有知识页都必须能回溯到某个 SRC。
- **source 页(原料摘要页)** — 每条 SRC 在知识页区的对应页面(页类型 `source`),承载该条原料的摘要与出处。**这是消费面可见性的焦点**——它可见是"答案带来源"的实现方式,也意味着保密文档的摘要对消费面可见(见 FR-13)。文中不再使用"源页"等其他说法。
- **综合页** — 由机器综合产出的知识页(页类型 `synthesis`),人审抽样的主要对象;**枢纽页也是综合页的一种**。文中不写作"合成页/synthesis 页"。
- **页面状态枚举** — 知识页的合法状态集 `{draft, stable, deprecated}`(以概要设计 §5.4 门 5 为准)。`skeleton` 是建图过程中的**中间态,不属于合法枚举**,必须在批内归一;遗留 `skeleton` 即判异常批次(见 FR-9/FR-11 门 5)。
- **水位线** — 每源的增量游标;推进即"已处理到此"。水位线是优化手段,**不是**漏捕与删除的唯一发现机制(见全量对账)。
- **keymap** — 源系统文档 key → SRC 编号的映射,与水位线同域存放;用于重捕判重与来源追溯。
- **state** — 流水线的运行状态文件集合:水位线、keymap、失败批次、批次报告。
- **建图** — 把原料编译为知识页并把页面挂进体系树的过程。执行建图的主体称**建图代理**。
- **枢纽页** — 体系树的目录节点(一种综合页),以独占行链接指向它的成员页。
- **体系树** — 由枢纽页与成员页构成的、可枚举可校验的知识组织结构;首版由源系统分类树翻译而来,此后增量维护。
- **独占行链接** — 挂载关系的持久形态:枢纽页内独占一行的成员链接,同时被写侧与只读结构层识别为体系边。
- **门(质量门)** — 批次提交前的自动质量校验,分阻断与告警两级;清单以单一配置文件为唯一来源。
- **批次** — 一次编排器运行;有全局唯一的批次 ID,该 ID 同时出现在状态文件、提交记录与告警中。
- **批次报告** — 每批的结构化运行报告(批次 ID、源、水位线推进、捕获与建图计数、门结果、体积、耗时),用于排障与审计。
- **OKF** — 本知识库采用的知识格式规范(okf-0.2),含页面模式校验与体系树工具。
- **消费面(只读面)** — 暴露给平台的只读检索工具集合,恰为 5 个工具:召回、检索、读全文、状态、质量检查(规范 ID 与契约见 FR-16)。
- **召回(recall)** — 消费面主检索工具 `wiki_recall`,按主题召回相关页。
- **状态工具 / 库健康检查** — 同一个东西:`wiki_status`(5 个只读工具中的一员)。文中"库健康检查""库健康"均指它——**它不是独立工具**,勿与"恰为 5 个"冲突。
- **冒烟** — 自动化健康探针,分两类:**工具集冒烟**(断言消费面工具集合恰为 5)与**召回冒烟**(批末用本批新页标题召回,期望非空)。
- **黄金问题集** — 每库 20–50 道人工编写的评测题,用于测量召回命中率;是判断"要不要上向量检索"的唯一依据。
- **专属 agent** — 平台上为每个库建立、默认绑定该库的 agent。绑定决定**默认可用性**,不是访问控制。
- **单写者** — 约束:任一 vault 任一时刻只允许一个写侧进程。
- **增量 / 全量对账** — 增量 = 按水位线取上游变化;全量对账 = 忽略水位线重扫源以发现漏捕、删除与改名,不重捕内容未变的条目。
- **spool / raw-inbox** — 两个不得混用的进料口:spool 是机器暂存(连接器产物,进捕获前),raw-inbox 是人工进料口。
- **BM(保密库)** — 第四个源:BM 保密网络安全知识文档,及其对应的 vault。文中"BM 库""BM 源""保密库"是**同一个东西的三种说法**,以"BM 库"为规范用法。
- **只读补丁** — 使消费面工具集收窄为 5 个工具的补丁序列,属受版本管理的交付件(见 FR-13/FR-22)。

## 4. 功能需求

### 4.1 数据抽取(模块一)

**描述:** 从四个源系统(Confluence、禅道、Nextcloud、BM 保密文档目录)按各自的协议与认证方式抽取内容,归一化为 markdown,落入 vault 的原料区。抽取是**增量为主**的,并且必须能区分"上游真的没变"与"我们没看见变化"。实现 UJ-1 的前置条件、UJ-2 的失败面、UJ-3 的联调对象。

**功能需求:**

#### FR-1: 四源增量抽取

系统能从四个源**各自独立**抽取增量条目:Confluence(REST)、禅道(REST)、Nextcloud(WebDAV)、BM 保密文档目录(文件系统)`[ASSUMPTION: 四源的协议与认证形态来自架构阶段的代码级取证,但源侧产品版本差异未逐项实测,见 §14 Q1–Q3]`。每个源有独立的运行状态;任一源失败不阻断其他源启动。

**可测后果:**
- 四个连接器可分别单独运行;停用任一源,其余三个源仍能正常跑批。
- 每源使用约定的增量信号:Confluence 取最后修改时间、禅道取最后编辑时间戳、网盘取 ETag(比较前剥离压缩后缀)、BM 取文件 mtime。
- 单批产出的每个条目都带**稳定的源系统文档 key**(wiki 页面 ID / 禅道数字 ID / 网盘相对路径 / BM 路径+内容 hash 组合)。
- 大 space 的对账按 space 分批执行,不因单次超时中断整批。

**范围外:**
- 源系统不支持增量信号时的降级策略(按源单独定义,属实施配置)。

#### FR-2: 归一化与源包落盘

抽取产物统一归一化为 markdown 加结构化头信息(标注源系统、出处 URL、版本、时间),再经写侧工具落入原料区形成 SRC 源包。Office/PDF 类文档**必须在上游**完成文本解析后才进入本系统。

**可测后果:**
- 每个 SRC 源包含提取文本、出处清单与附件;**BM 库的源包不含原件本体**(见 FR-6)。
- 落盘后,该 SRC 的内容在后续任何批次中字节不变(唯一例外见 FR-6)。
- 直接写文件系统绕过写侧工具产出的页面,会被质量门第 4 项检出(见 FR-11)。
- **生成物禁止手编**:登记表与目录/日志类生成页由工具全量重写,**人工编辑会在下一次写入时被抹掉**。因此本系统的体系可枚举性靠查询承担,不靠人工维护目录页(addendum §4.5)。

**范围外:**
- 在流水线内做文档格式解析(解析必须是上游前置步骤)。

#### FR-3: 增量判定与幂等(水位线 + 内容指纹 + keymap)

每次捕获后登记 `{源 key, SRC 编号, 内容指纹, 捕获时间}`。同一 key 重捕且内容指纹未变则**跳过**,不新建 SRC。

**可测后果:**
- 同一 key 重复抽取且内容未变:不产生新 SRC,不产生新知识页。
- 顺序契约成立:捕获全部成功 → 水位线推进 → 建图;先推水位线的实现路径被禁止。
- 中断后重跑同一批,结果与首次成功执行一致(幂等)。
- keymap 与水位线同域存放、同受备份保护。

#### FR-4: 上游内容变更的传播

同一 key 内容指纹变化时,新建 SRC,并在新 source 页标注 `supersedes` 指向旧 SRC,旧页置 `deprecated`。

**可测后果:**
- 变更后,新 SRC 的 source 页可读出被替代的旧 SRC 编号。
- 旧页状态为 `deprecated`,不再作为消费面首选结果。

#### FR-5: 周期全量对账(删除与改名发现)

系统按源**周期性地**忽略水位线重扫源,发现漏捕、删除、改名与移动,产出删除清单与移动清单落入 state 并告警。**一期不自动删页**——人工确认后置 `deprecated`。

**可测后果:**
- 全量对账**不重捕**内容未变的条目(不产生 SRC 洪峰)。
- 对账产出的删除/移动清单落 state,可审计、可复算。
- 未确认的删除不会导致任何页面消失或状态变更。
- 上游重命名一个文档后,对账能报出该变化(不依赖水位线)。

**范围外:**
- 自动删页;物理删除任何知识页。

#### FR-6: BM 保密库的抽取白名单与原件隔离

BM 库的抽取范围由**白名单**限定,每批新增文件清单**人工审**。BM 原件(Word/PDF 本体)**不进 vault**,原料区只存提取文本与来源引用(系统/路径/hash),原件留在源存储。

**可测后果:**
- BM vault 内不存在原件二进制文件。
- 每批次的报告中含该批新增文件清单,且该清单在批次提交前已被人工确认。
- 误捕处置有既定路径:经审批对该库做历史改写(这是"原料只增不改"的唯一例外)。

**范围外:**
- 自动判定某文件是否敏感;白名单由人工维护。

### 4.2 知识编译与质量门(模块二)

**描述:** 把原料编译成知识页,把页面挂进体系树,并在提交前用质量门拦截结构性问题。这是本系统的核心取舍所在(见 §1 赌注):编译质量靠**流程纪律 + 自动门 + 抽样人审**三层保障,而不是靠单次生成的质量。实现 UJ-2 与 UJ-4。

**功能需求:**

#### FR-7: 单写者排他

任一 vault 任一时刻只允许一个写侧进程。任何写侧序列(捕获、建图、校验、人工建库会话)必须先取得排他写锁;获取失败即非零退出并告警,**禁止重试绕过**。

**可测后果:**
- 并发发起两个写侧进程时,恰好一个成功,另一个明确失败(非静默)。
- 锁中带**可排障的元数据**:持有者进程标识、批次 ID、获取时间、来源(流水线 / 人工会话)。排障时能回答"谁持着锁、在跑哪一批",不需要猜。
- 人工建库会话的**操作顺序固定**:先停调度、再显式取锁;顺序颠倒即视为操作违规。
- 流水线遇到人工会话持有的锁时,记录为 `skipped_locked`——不计失败、不推水位线。
- 超期(>24 小时)的僵尸锁由流水线回收并告警。
- 四个源的调度是串行的,不存在两个源同时写不同 vault 之外的并发现象。

**范围外:**
- 多写者并行编译同一库。

#### FR-8: 首版体系树与增量维护

每库初始化时,按既定翻译法把源系统分类树转换为体系树(原分类节点 → 枢纽页,原父子关系 → 独占行链接)。此后体系由建图代理**增量维护**,并经质量门第 3 项复核。

**可测后果:**
- 初始化完成后,源系统的每个顶层分类在该 vault 内有对应的枢纽页。
- 新增知识页挂进体系后,可被体系的成员查询枚举出来。
- 体系调整(改挂载关系)有明确动作归属:由建图代理执行,经门 3 复核。

#### FR-9: 建图代理式知识编译

建图采用**先搜后建**:对每份原料先做检索,查明是否已有相关页面与概念,再建或更新页面(选类型、挂枢纽、建立双向链接)。批内统一做状态归一,把非法的中间状态映射到合法枚举。

**可测后果:**
- 本批每份原料最终产生或命中至少一个知识页(无原料被静默丢弃)。
- **批次结束判据**:本批 keymap 中每个 SRC 对应的 source 页状态均非 `skeleton`;存在 `skeleton` 即按异常批次处理(`skeleton` 是建图中间态,不属合法枚举 `{draft, stable, deprecated}`,见 §3 与 FR-11 门 5)。
- 本批新建页面**均被某个枢纽页以独占行链接挂载**——允许存在未被挂载页的批次数为 0。
- 提交后不存在状态落在合法枚举之外的页面。
- 建图使用**既定纪律提示词**资产;该资产由建库指南与写侧纪律手册派生并随仓库版本管理。
- **模型不可用 = 批次失败**,不存在"静默降级为不编译"的路径;流水线启动与每批开跑前断言模型配置形状正确(模型标识必须是含 provider 与 id 的对象形态,字符串形态会被静默忽略)。
- **必设配置键全部显式声明**,缺任一键即视作初始化缺陷并使该库的批次无法开始;该项是初始化健康检查的一部分,不是文档建议。键清单见 addendum §4.2——其中合成语言与链接校验等级**必须显式钉为中文与严格模式**,因为二者的默认值(英文、告警级)**不会报错,只会静默产出不合要求的语料**。
- 建图工具**不得落入"返回原料供调用方自行综合"的降级路径**——该路径在无人值守下等价于不编译。

**范围外:**
- 用写侧工具的内置自动路径替代本流程(见 addendum 的取舍记录)。

#### FR-10: 批次契约与失败隔离

每次编排器运行有唯一批次 ID(`<源>-<UTC 起始时间戳>-<序号>`),该 ID 写入状态、产物、提交信息与告警。失败批次**仍然提交**(只提交本批路径清单,禁止全量暂存提交),失败明细落 state;已建页面保留待修。

**可测后果:**
- 任取一条告警、一条提交记录、一份批次报告,都能对上同一个批次 ID。
- **提交范围是通用约束,不分成功与失败**:一律只提交本批路径清单,**禁止全量暂存提交**——成功批次同样不得夹带无关改动。
- 失败批次的提交只包含本批路径清单——不含其他批次的改动、不含无关文件。
- 单源失败不阻断其他源的批次。
- 失败批次**不推进水位线**;重跑后可正常推进。
- 提交信息中可区分成功/失败批次。
- **仓边界明确**:每个库一个独立仓库,库外的流水线状态、日志、人工进料口与本仓跟踪范围互不嵌套。

**范围外:**
- 全量暂存式提交(无论成功批次或失败批次)。

#### FR-11: 阻断级质量门

批次提交前执行质量门,门清单以**单一配置文件为唯一来源**(门与告警共读同一份配置,禁止各自硬编码)。阻断级门至少包含下列 7 项:

| # | 门 | 判据 |
|---|---|---|
| 1 | 链接与结构检查 | 断链、孤儿页清零;歧义/矛盾/缺口分类处置(不得丢弃) |
| 2 | 模式校验 | 格式规范的模式校验通过 |
| 3 | 体系复核 | 本批新页必须被某个枢纽页约束(以成员查询为准,**不以目录树可达性为判据**) |
| 4 | 生成物外页面 | 磁盘上存在但不在生成物登记中的页面 = 绕过写侧工具写入的证据 |
| 5 | 状态归一 | 本批页面状态落在合法枚举 `{draft, stable, deprecated}` 内(以概要设计 §5.4 门 5 为准;`skeleton` 不合法) |
| 6 | 原料不可变 | 与批次前基线快照比对(不使用裸版本控制差异——首批发无基线) |
| 7 | 库健康 | 库健康检查无阻断级诊断,且格式版本声明在位 |

**可测后果:**
- 任一门不通过 → 该批次为失败批次,走 FR-10 的失败隔离路径。
- 门清单的增删只需改一处配置,门与告警行为同步变化。
- 门 3 的判据可复算:对本批页面执行成员查询,结果集与门结论一致。
- 模式规范**不得放宽**(见 §13.3)。

#### FR-12: 抽样人审

每批的**综合页抽样清单**随批次报告归档,供人工做语义层检查。机械性错误由门兜底,人审聚焦于"机器综合的内容是否忠实、挂载是否合理"。

**抽样规则(必须可执行,不留"抽样"二字了事):**
- **样本构成 = 本批全部新建综合页 + 从本批其余新页中随机抽取 N 页**(N 的取值部署期钉死并记录;新建综合页**不抽样、全审**,因为它们是机器综合程度最高、最易出语义错误的一类)。
- **抽样的时机在提交后、下一批开始前**——滞后窗口上限 = 一个批次周期。理由是门在提交前无法做语义判断,把全部语义检查前置会阻塞流水线。**该滞后窗口是已知且被接受的取舍**:提交与消费可能在人工看到清单之前发生,若某页被消费到且事后被打回,处置方式是置 `deprecated` 而非撤回(见 FR-5 的同类原则)。
- **回填字段固定**:`{页面 ID, 问题类型, 处置结论, 审阅人, 日期}`,写入 state 的批次人审记录,随批次报告归档;下一批开工时读取该记录,把打回页纳入修正范围。

**可测后果:**
- 每份批次报告含本批抽样清单,且清单按上述规则生成(可由批次数据复算)。
- 人审记录含固定字段,可按页检索。
- 打回页在下一批被修正或显式说明不予修正——不存在静默丢弃。
- 抽样清单为空的批次(如本批无新建页)在报告中显式标注"本批无人审样本",不记为"已审"。

### 4.3 查询应用(模块三)

**描述:** 把知识库以上述**只读**方式暴露给平台,让专属 agent 能检索并读全文。实现 UJ-1 与 UJ-3。消费面是本系统对外的唯一业务接口。

**功能需求:**

#### FR-13: 只读消费面

每个库在 okf-kb 服务器上以**只读模式**起常驻 HTTP 服务,只注册五个工具:召回、检索、读全文、状态、质量检查(长页自动分页)。只读模式的落地形态是 **bundle 只读补丁**(2026-10-14 已裁定并落地实测),受版本管理与冒烟守护。

**可测后果:**
- 以只读模式启动的服务,暴露的工具**恰为 5 个**(工具集冒烟断言)。
- 写侧工具在只读模式下**物理不注册**——平台工具列表里根本没有它们,无从调用(不是"调用时报错")。
- 召回结果**只含本库内容**,不合并任何个人库;且库根路径未显式设置时**启动即失败**,不静默回落到个人库目录。
- **只读补丁的真实职责 = 只做工具注册裁剪**(2026-10-14 对照 bundle 代码核实):白名单外的工具不注册,其余行为保持原样。三条旧宣称**均未实现,不得依赖**:①"关闭个人库合并"——补丁不管合并,**唯一防线是服务端 env `WIKI_HOME` 与 `WIKI_ROOT` 同置**(对照实验:不设时宿主个人库内容会混入召回结果);②"显式跳过启动期索引恢复"——未实现(实测服务启动/重启本身不写库,风险有限);③"裁剪返回中的宿主路径字段"——未实现,召回返回的 `path` 即服务端绝对路径(实测样例:`/…/.llm-wiki/wiki/concepts/x.md`)。
- **质量检查工具(`wiki_lint`)是只读面的已知例外——它带写入能力**(2026-10-14 实测):①默认调用即写库内 2 个文件——`outputs/lint-<日期>.md` 报告与 `.discoveries/gaps.json`;②`auto_fix=true` 时追加写 `meta/` 元数据(registry/events/index/log)与 `wiki/log.md`,并在"某缺失页被 ≥2 个页面引用"时**创建 stub 知识页**(`status: stub`);③`auto_fix` 参数对消费方**完整暴露**(平台侧 LLM 可见可调)。它不改已有页内容,但"创建 stub 页"是实质内容写入。若消费方不接受任何写行为,须把补丁白名单收窄为 4 个(裁掉 `wiki_lint`)——**该收窄未做,现状 5 个含 lint**;BM 库评审须纳入此点。
- 工具集冒烟脚本对**补丁序列**做断言:完整模式 16 个工具、只读模式恰 5 个;任一断言失败即视为补丁丢失,**不得静默通过**。
- **启动断言四项**(与只读补丁同批交付验收;**2026-10-14 现状:补丁未实现此四项,属待办**):①库根路径已显式设置;②解析结果**等于**本库根;③库标识文件存在;④**拒绝任何指向其他库子树的路径**。任一不成立即启动失败。
- **硬约束:只读补丁落地并冒烟验证之前,禁止在平台注册任何 server**——完整模式工具集含 11 个写侧/运维侧工具,裸注册即把写能力暴露给消费 agent。

**可见性取舍(显式声明,非疏漏):** 消费面**能**读到 source 页——这是"答案带来源"的实现方式,也是 UJ-1 高潮成立的前提。代价是:原料的摘要与出处(而非原件)对消费面可见,BM 库亦然。该取舍在 v1 **不收窄**;若安全评审要求"只暴露编译产物"(即排除 `sources/` 层),须收窄本实现并重估 UJ-1。

**范围外:**
- 消费面开放原料原件与附件(只开放知识页与 source 页)。

`[NOTE FOR PM]` 只读面的实现路径曾有一条**待定分歧**(见 §14):给工具包打只读补丁,还是走平台侧既有的工具白名单能力。**2026-10-14 已裁定为「bundle 只读补丁」并落地实测**(§14 Q8 已闭)。无论哪条路线,**"注册前必须验证恰为 5 个工具"这一验收判据不变**。

#### FR-14: 平台接入配置

在平台后台以配置方式建立四条 **url 型** server 记录,指向 okf-kb 服务器上各库的只读 HTTP 服务(服务由 okf-kb 侧常驻,见概要设计 §6.2)。平台代码零改动,且**不再需要容器编排变更**(无 compose 挂载、无容器重建)。

**可测后果:**
- 四条 server 均为 active;每条起会话执行"库健康"工具能成功返回**它自己的库**。
- 工具名称按平台规则呈现为 `mcp__okf_wiki_<源>__<工具>`(连字符被平台规则转为下划线;管理侧显示的集合名称保留连字符)。
- 库根路径与个人库根路径(同路径)在**服务端** env 配死(`WIKI_ROOT`=`WIKI_HOME`,见概要设计 §6.2)——HTTP 形态下平台侧不再传 env,该防线完全在 okf-kb 服务器。
- **库文件不出 okf-kb 服务器**:平台无任何 vault 副本、无挂载;访问控制 = **网络面收敛**(防火墙只放行平台服务器,或认证反代;见概要设计 §6.2 注 2)。
- 平台侧超时**显式配置**(数据库层默认值 120 秒**不生效**,实际回落到 **300 秒**;不显式写即按 300 秒运行)。三个超时值须在部署期一并钉死并记录:平台单次调用超时、单工具调用超时、批次整体时限(见 §14)。
- 服务可达性冒烟列入部署验收:改名/未启用/未绑定等配置错误在平台侧是**静默降级**(无工具但不报错),只能由冒烟兜住;服务停着 = 平台连不上(报连接/工具错误)。
- **负向断言(与正向同等重要)**:①平台容器内**不存在**任何知识库目录与文件;②okf-kb 服务器上服务进程确为只读(`WIKI_ROOT`=`WIKI_HOME`,工具列表恰 5 个)。不能只靠"没配置应该就没有"的推断。
- **资源预算重估**:HTTP 形态下工具进程树只在 okf-kb 服务器上(每库一个常驻 node 服务),平台侧不再每会话起进程树;okf-kb 服务器需预留每库 1 个常驻进程与并发检索的 CPU/内存,由 okf-kb 侧确认。

#### FR-15: 专属 agent 绑定

每个库在平台上建立专属 agent 并默认绑定对应 server;跨源问答由同一 agent 同时绑定多个库实现。

**可测后果:**
- 每个库**有且仅有一个**专属 agent 默认绑定其 server。
- 同一 agent 绑定两个库时,两个库的工具同时可用(跨源问答成立)。
- 文档中明示:绑定 = 默认可用性,**不构成访问控制**(见 §9.1)。

#### FR-16: 检索链路与工具契约

标准消费流为**召回定位 → 读全文**。五个工具的契约如下(规范 ID 即代码与配置中使用的名字;平台呈现名见 FR-14):

| 工具 | 规范 ID | 用途 | 输入 | 返回 |
|---|---|---|---|---|
| **召回** | `wiki_recall` | **主检索**:按主题打分召回相关页(分块打分 + 字段加权 + 伪相关反馈) | `query`(必);`max_results`(默认 5,**上限 10**) | `matches[]`:`{id, title, type, preview(~200 字符), path, score}` |
| **检索** | `wiki_search` | **精确匹配**登记表(页 ID/标题/类型/状态/标签/别名/召回触发词):已知目标时的快速定位,无打分无反馈 | `query`(必);`type`(可选过滤) | `matches[]`:`{id, title, type}` |
| **状态** | `wiki_status` | 库健康与统计:读**预建元数据**,不扫文件 | 无 | `{totalPages, byType, orphans, gaps, health}`,health ∈ `✅ Good / ⚠️ Warning / 🔴 Empty` |
| **读全文** | `wiki_read` | 按 `id` 读整页;长页按字符窗口分页 | `page_id`(必);`offset?`;`limit?`(默认 6000,**上限 20000**) | 正文 + `has_more` 与续读 `offset`;只开放 `wiki/` 层并拦截路径穿越 |
| **质量检查** | `wiki_lint` | 库健康深度扫描(孤儿/断链/矛盾/缺口)并写报告;**带写入能力,见 FR-13** | `auto_fix`(布尔,可省;为真时写库) | 检查结果摘要 + 库内报告文件路径 |

**分工唯一:** 召回 = 不知道确切名字时用;检索 = 知道确切名字/术语时用。二者不可互相替代,消费面不提供第三个检索工具。**`检索` 同时是写侧"先搜后建"(FR-9)的查重工具**——同一工具在写侧与读侧共用,但只读模式下写侧用法不可达。

**只读模式下的返回形状(2026-10-14 实测口径)**:`path` 字段**未裁剪**,即服务端绝对路径;`vaultLabel` 在 `WIKI_HOME`=`WIKI_ROOT` 配好后不出现(个人库合并关闭靠 env,不靠补丁——见 FR-13)。

**可测后果:**
- 一次典型提问可由"召回 + 读全文"两步完成,无需第三步工具。
- 召回返回的 `id` 可直接作为读全文的入参(无需二次检索)——这是"足以定位"的可测化定义。
- 长页分页可续读:分页边界处 `has_more` 为真且携带续读 `offset`,连续读取可拼出完整正文。
- `max_results` 上限 10 生效;请求超过上限时按上限裁剪。
- 返回形状相关配置项的变更在版本记录中可查。

### 4.4 运维与可观测

**描述:** 让流水线在无人值守下可信:能证明它跑了、能复盘单次运行、能在库"看起来是空的"时区分"真没数据"与"检索坏了"。实现 UJ-2 的后半段与 §13 的运行要求。

**功能需求:**

#### FR-17: 运行可观测三件套

三层记录**同挂批次 ID**:(a) 完整运行日志——连接器、建图代理、门、版本控制各阶段明细,按批次归档;(b) 结构化批次报告;(c) 心跳文件。

**可测后果:**
- 任取一个历史批次,能仅凭归档材料完整复盘一次运行(谁在什么时候做了什么、失败在哪一步)。
- 批次 ID 在日志、报告、心跳三处可关联。
- **门的全部产物以批次 ID 与源命名**(不按日期命名)——同一天多批不会互相覆盖,事后读到的必是该批次的结论。
- 门的结构化结果单独落盘;告警只读该结构化结果,不去解析文本报告。
- 日志保留不少于 90 天且配置了轮转,且轮转有明确的**责任归属**。

#### FR-18: 告警

心跳超阈值、或某源超过约定时限没有成功批次 → 告警(须能区分"流水线没跑"与"没有新数据");宿主磁盘使用率超 80% 告警。告警通道启用是**部署验收项**,含一次**真实演练**;未启用时降级为非零退出码加状态记录,**不得静默**。

**可测后果:**
- 演练可证明:人为制造的心跳缺失能触达责任人。
- 告警消息字段集合**仅含**批次 ID、源、门代码、计数——**不含**文档标题、路径、正文。
- 告警通道不可用时,失败仍以非零退出码与状态记录留下痕迹(可断言)。
- 连续两个源超过时限无成功批次时,能区分出哪个是"没跑"哪个是"没数据"。
- 陈旧度阈值写死为具体数值(不允许留空或"待定")。
- 告警**收件人形态**在部署期确定并记录(现有告警能力仅支持定向私信,收件人清单须显式维护)。

#### FR-19: 召回冒烟

每批结束时,用本批新页标题做一次召回,期望**非空**。

**可测后果:**
- 检索读不到生成物登记时**静默返回空结果**这一失败模式能被探针捕获——**召回冒烟是探针**(产出信号),**库健康检查是裁定入口**(判定性质);两者分工不同,不并称"唯一"。
- 冒烟失败 → 该批次告警。
- 索引刷新在发布步骤中**显式可见**,有明确的执行者与失败处置(不再作为隐含步骤)。

#### FR-20: 召回基线评测(黄金问题集)

每库建立 20–50 道评测题,覆盖三类:**直问、同义改写、跨页综合**。三类均须出现,且**同义改写类不少于 1/3**——它是"要不要上向量检索"这一决策的触发读数来源,样本太少则该读数不可信。测量**召回 top-5 含期望页**的命中率(top-5 即 `wiki_recall` 的默认 `max_results`,见 FR-16)。达标线为总体 ≥80%(起步值,跑 2–4 周后按实际分布校准)。改写子集命中率**单独统计**。上线后按对账节奏周期性复跑,监测召回漂移。

**可测后果:**
- 每库有题集文件与基线读数存档,达标判定可由存档数据复算。
- 改写子集命中率单独可读。
- 命中率低于达标线时,触发向量检索评估(见 §5 与 §6.2)。

**范围外:**
- 自动化生成评测题;v1 题集由人工编写。

#### FR-21: 备份与恢复

**恢复域 = 库目录(含事件溯源记录)+ 流水线状态(水位线、keymap)+ 流水线配置(凭据)**,三者同域备份。

**重建方向(单向,不可倒置):** 状态**可由库重建**(keymap 可从原料区的源包加源系统再扫描重算);库**不可由状态重建**。因此两类丢失的后果不对称:
- **丢状态** → 可重建,但**必须以对账方式重算并人工确认**,不得直接空跑(空跑会让水位线归零、触发一次全量重捕)。
- **丢库** → 只能全量重捕;若源侧条目已删除,则**永久漏捕**。

**可测后果:**
- 恢复步骤可执行:取回库仓库 → 恢复配置 → 缺生成物登记时重建 → 起服务 → 召回冒烟通过。
- **状态重建路径存在且可演练**:从原料区加源系统再扫描重建 keymap,并经人工确认。
- 目标:RPO ≤ 1 批、RTO ≤ 2 小时(部署期确认)。
- 每季度一次恢复演练,演练记录归档。
- 检索索引**不入库仓库**且可重建——恢复时不依赖它的历史版本。

#### FR-22: 升级与回滚

版本记录含:上游来源版本、**补丁清单**、校验和。升级 = 离线包替换 + 补丁重放 + 工具集冒烟(完整 16 工具 + 只读模式恰 5 个)+ 复检。窗口 = 停只读服务且无批次运行。回滚 = 保留上一版的工具目录整份替换回去。

**可测后果:**
- 升级后工具集冒烟通过(两个断言:完整模式 16、只读模式 5)。
- 回滚后系统可用,冒烟通过。
- 库兼容性检查项(格式版本、登记版本、索引存储版本)在升级清单中逐项确认。
- 索引重建**禁止**使用全量模式(内网环境会触发模型下载)。

## 5. 非目标(显式)

- **不做物理隔离或文件级强权限。** 隔离强度 = 独立库 + 独立服务 + 独立配置的**逻辑隔离**;不含用户级/文件级强制。BM 库的暴露面**是待 §9.1 裁定的风险**——裁定为路径 B 并完成书面签署前,一律按"未接受"处理(见 §9.1)。
- **v1 不做向量语义检索。** 先上线词法检索;是否引入由黄金问题集读数触发(见 FR-20),不由偏好决定。
- **不做平台 UI 改造。** 平台代码零改动——只有后台配置变更(url 型 server 记录;2026-10-14 起无挂载面)。
- **不做跨库统一知识图谱、跨库体系枢纽页。** 跨源关联靠一个 agent 绑多库。
- **不做自动删页。** 删除是业务信号,误删不可逆;对账结果只告警,确认后置状态。
- **不用平台自身的调度器做编排。** 理由见 addendum(进程边界与解耦)。
- **v1 不把只读结构层的检索能力暴露给消费面。** 避免双 MCP 面;代价与回退条件见 §6.2。
- **不生成"全库目录树"作为验收依据。** 体系可枚举性由成员查询承担,不以目录树可达性为判据。
- **不回写源系统。** 知识库是单向只读采集。
- **不服务内网之外的用户。**

## 6. MVP 范围

### 6.1 范围内

- **P0 单源骨架**:选定一个源(建议 Confluence)`[ASSUMPTION: 首源建议取 Confluence;若 Q1/Q7 盘点显示该源不可用,首源可换]`打通"初始化 → 抽取 → 捕获 → 建图 → 门 → 提交"全链路;okf-kb 侧完成只读补丁 + 工具集冒烟 + 只读服务常驻;平台侧完成 1 条 server 注册、1 个专属 agent 默认绑定。**server 记录随源增量追加**——P0 只建首库 1 条,不要求一次到位。
- **P1 四源铺开**:其余三源各走一遍 P0 流程上线(BM 源额外加白名单与人审),server 记录随各源逐条追加。
- **P2 调度与告警**:定时编排、增量水位线、告警通道接线、心跳与陈旧度告警,并完成一次告警演练。
- **召回基线评测**:每库建立黄金问题集并取得基线读数(FR-20)。
- **首次恢复演练**:按 FR-21 步骤实操一次并归档记录。

**MVP 出口标准:** 四库四条 server **验收清单**全部通过(清单定义见下);每库可问答(带来源);四库质量门全绿;工具集冒烟与召回冒烟通过;四库召回基线读数均达标;告警演练与恢复演练记录归档。

**"验收清单"的定义**(引自概要设计 §6.2,以该处为准;本文不重述细则):
1. 4 条 server 均为 active;
2. 每条 server 起会话,状态工具成功返回**本库**;
3. 每条的**工具列表恰为 5 个**;
4. 零副本与只读负向断言通过(平台侧不存在任何知识库目录与文件;okf-kb 侧服务 env 确为 `WIKI_ROOT`=`WIKI_HOME`);
5. 每条 server 的启动冒烟通过(无静默降级)。

**基线达标线的版本口径:** 出口要求的"召回基线读数达标"以 **MVP 冻结时刻的达标线版本**为准;§7 SM-1 的 80% 会在跑 2–4 周后按实际分布校准——**校准不得反向放宽已冻结的出口判据**;若确需下调,须由需求方书面接受新线并记录,不得默认沿用。

### 6.2 范围外(MVP 不做)

| 项 | 理由 | 触发条件 |
|---|---|---|
| 向量语义检索 | 先词法上线,用读数决策 | 黄金问题集总体命中率低于达标线(或校准后的线) |
| 消费侧体系语境注入(只读结构层检索) | 避免双 MCP 面;代价是弱模型可能缺少体系上下文 | **可观测代理信号**:消费侧抽样问答中"答非本库"或"答案缺来源"的比例超过约定阈值(随 P2 抽检机制建立后开始记录);或 §14 复评时点到期 |
| 跨库统一知识图谱 | 一个 agent 绑多库已足够 | 出现跨库体系需求 |
| 根目录页体系区段守护 | 门不以目录树可达性为判据 | **并入 §14 复评时点**:P3 巡检清单固化时一并评估是否需要目录树全貌;若届时仍无需求则关闭该项 |
| 平台 UI 演进(多选绑定、库状态展示) | 平台代码零改动原则 | 需求方提出时 |
| 各源抽取范围精细化 | 属实施配置项 | 随 P1 各源上线 |
| 备份远端与快照策略 | 恢复域已钉死(FR-21) | 随 P3 运维完善 |
| 建图提示词资产完善 | 属实施内容 | 随 P0 建图代理联调 |

`[NOTE FOR PM]` §6.2 中"向量语义检索"是最可能被提前拉进来的一项。拉进来的代价不只是开发量,还包括内网环境下额外的模型依赖与容量占用;建议坚持"由读数触发",不要在 P0 阶段为它留架构口子。

## 7. 成功指标

### 主要

- **SM-1: 召回命中率。** 每库黄金问题集,召回 top-5 含期望页的命中率,总体 **≥80%** `[ASSUMPTION: 80% 为起步线,跑 2–4 周后按实际分布校准;校准前不构成承诺]`。验证 FR-16、FR-20、FR-9。
- **SM-2: 四库消费可用性。** 4 条 server active,每库专属 agent 能完成"提问 → 带来源答案";验收清单(§6.1)全通过。验证 FR-13、FR-14、FR-15。
- **SM-3: 流水线可靠性。** **连续 N 个计划批次**成功(不含 `skipped_locked`),且每个失败批次都有告警与可追溯报告;N 于批次节奏确定后钉死(建议日批取 7、周批取 4)`[ASSUMPTION: 批次节奏未定,故 N 未定;见 §14]`。验证 FR-10、FR-11、FR-18。

### 次要

- **SM-4: 知识新鲜度。** 源变更到可被召回的时间,p95 ≤ `[ASSUMPTION: 24 小时]`(最终随批次节奏评审确定)。验证 FR-1、FR-3。
- **SM-5: 批次可观测覆盖率。** 100% 的批次有结构化报告与对应提交记录。验证 FR-10、FR-17。
- **SM-6: 告警有效性。** 演练触达率 100%;误报率在运行 4 周后建立基线。验证 FR-18。
- **SM-7: 恢复能力。** 季度演练实测 RTO ≤ 2 小时、RPO ≤ 1 批。验证 FR-21。
- **SM-8: 来源可追溯完整率。** 抽样知识页 → 其 source 页 → 源系统 key 的溯源链完整率 = **100%**。这验证 §1 赌注的第二条腿("每一条知识都能回溯到它的原始出处")。可由门 3 与门 6 的产物复算,不需要新的采集。验证 FR-2、FR-4、§9.4。

### 反向指标(明确**不**优化)

- **SM-C1: 知识页数量增长。** 页数增长不等于知识增长,以它为目标会鼓励碎片化页面、稀释检索精度,与"体系可枚举"的赌注相悖。制衡 SM-1。
- **SM-C2: 召回返回条数。** 加宽返回条数能轻松抬高命中率,代价是消费端信噪比。制衡 SM-1。
- **SM-C3: 人工介入时长。** 不得为压低人工时长而放宽门标准或跳过抽样人审。制衡 SM-3。
- **SM-C4: 批次数 / 运行频率。** 空转批次不产生价值;不得为"看起来在跑"而提高频率。制衡 SM-3。

## 8. 跨功能非功能需求

- **NFR-1 消费面可用性:** 消费面只读(已知例外:`wiki_lint` 的写行为,见 FR-13),不因流水线写操作而不可用。**索引的刷新与重建一律属于写侧职责**——消费服务不承担索引维护,因此索引必须在发布前由生产线准备好。`[NOTE FOR PM]` **索引在召回链路上的必要性存在口径分歧**(输入评审有"消费读路径依赖索引"与"召回实际读生成物登记、索引非必要条件"两说),本 PRD **不裁断哪一说成立**:无论结论如何,**发布清单必须包含索引刷新步骤**,且召回可用性**以冒烟探针为准,不以"索引缺失时仍应可用"的推断为准**。该分歧以一次命令级实测裁定(addendum §3.3)。
- **NFR-2 检索响应:** 召回与读全文的单次响应时间须在部署期实测后设阈值并记录 `[ASSUMPTION: 阈值定为 p95 ≤ 5 秒,含分页读取]`。单页读取须能在**平台单次调用超时**(当前实际值 300 秒,见 FR-14)内完成;超时分页续读。
- **NFR-3 建图负载限流:** 建图并发上限 1–2,且在夜间低峰调度,不与平台交互业务争用模型服务容量。
- **NFR-4 批次时限:** 每批设有整体时限,单次工具调用设有显式超时(不依赖默认值);超时按批次失败处理,不留悬挂进程。具体数值为部署期钉死项(见 §14 超时预算)。
- **NFR-5 容量:** 四源文档量级与容量预算为实施前盘点项(见 §14 Q4/Q7)`[ASSUMPTION: 文档量级未知,容量预算须实施前盘点]`;盘点结果决定单库体积上限与保留策略。每批次记录各部分的体积增量,宿主磁盘占用超 80% 告警;保密库单独设容量预算。
- **NFR-6 幂等与可重跑:** 任何批次可原样重跑并收敛到一致结果;原料不可变是重跑可信的前提。(判据见 FR-3 与 FR-10,本条不另立。)
- **NFR-7 离线可部署:** 全部组件在无外网环境可部署与升级;任何需要联网的路径(模型下载、包安装)在内网路径上被禁用。流水线运行时的形态与依赖来源须在实施前钉死(离线环境无法临时安装)。
- **NFR-8 版本可回滚:** 工具目录整体可回滚;库格式兼容项在升级清单中逐项确认。(判据见 FR-22,本条不另立。)
- **NFR-9 无静默失败:** 系统内不得存在"失败但不留痕"的路径——失败必须表现为非零退出码、状态记录或告警之一。

## 9. 安全、合规与数据治理

### 9.1 隔离等级与 BM 决策点

**隔离等级 = 依赖层逻辑隔离**:独立库 + 独立服务 + 独立配置。**不含**文件级/用户级强制。

平台**无 MCP 库级授权**——任意登录用户可通过会话参数直接挂载任意 active server,专属 agent 绑定只是默认值、不是访问控制。这意味着**按当前平台形态,BM 库对平台全员可见、可查**。

`[NOTE FOR PM]` **这是本 PRD 里最重大的决策点,必须在 P0 启动评审会上择一,不能留白。** 它与 §14 决策组其余各项(Q8/Q9)分属两级:那些是**实施前提**,本项是**范围与合规裁定**。**裁决人:需求方**(安全评审出具意见、平台团队评估路径 A 工作量;见 §10)。路径 A 的排期申请由需求方发起并跟踪——不是转给平台团队即算交付。

架构已在**设计层面**采纳"风险接受"(spine 标 `[ADOPTED]`),但独立评审(安全与运维视角)指出:**仅在设计文档里标注接受不构成风险处置**,必须落到"真隔离"或"有签署的接受"二者之一。本 PRD 据此把它升级为需正式裁定的决策点:

| 路径 | 内容 | 代价 |
|---|---|---|
| **A. 真隔离** | 平台侧改造:非管理员只能加载其所选 agent 绑定的 MCP;枚举接口按用户过滤;保密库不进通用勾选列表。**改动涉及会话装配的多条路径** | 平台代码改动(跨仓,违反"平台零改动"原则),需平台团队排期;**且会一并收窄平台现有的"会话级自由勾选 MCP"产品行为**——不只是新增校验,是行为变更 |
| **B. 风险接受**(架构原采纳项) | 保持平台零改动,BM 库以通用 server 注册;**BM 库对平台全员可见可查作为已接受风险**,由需求方与安全评审**书面签署** | 保密文档的可见面放大到平台全部登录用户;须同时接受 §9.1 下方的"取回即扩散"边界 |
| **C. 缩小范围** | BM 源移出 v1,其余三源不受影响 | 需求方少一个知识库 |

在决策落地(路径 A 完工并验证 / 路径 B 签字 / 路径 C 确认)之前,**BM 库不得在平台注册**。这不是"以后修"的技术债——它决定 BM 知识进不进系统。**该决策落地后须回写 spine**(见 §0 冲突表第 1 行)。

无论选哪条,**配套硬约束不可协商**:
- BM 原件**不进 vault**(见 FR-6);BM 库不配置远程仓库。
- BM 抽取范围白名单 + 每批新增文件清单人审。
- 宿主侧 BM 库独立用户/组、权限 0750、禁 world-readable。
- 误捕处置 = 经审批对 BM 库做历史改写(「原料只增不改」的唯一例外)。
- **最小可见面**:平台侧零副本、无挂载(库文件只在 okf-kb 服务器);okf-kb 服务器上:服务以独立账户运行、库目录 0750(BM 独立组)、只读模式配死。

**"解耦"的准确边界(须如实陈述):** 生产线与平台的解耦成立于**业务数据面**——库目录是唯一业务接口,平台不参与建库。**2026-10-14 HTTP 形态下边界反转**:消费侧不再是"平台容器内拉起的 MCP 进程"(旧 stdio 的容器视图继承问题随之消失),而是**平台向 okf-kb 服务器发起的 HTTP 客户端**——库文件不出 okf-kb 服务器,平台侧零副本。新边界如实陈述:
- 平台到达不了 vault(只有 HTTP 接口),旧形态"消费进程能看到平台凭据文件、全部用户数据目录与服务源码"的风险**不再适用**;取而代之的是 okf-kb 服务器成为数据驻留点,其主机安全与权限口径由 §9.2/§9.3 承担,并要求平台团队更新其运行边界文档的层级口径。
- 平台侧新增留痕面(会话消息与工具返回内容落平台 PG、模型网关载荷)是平台固有行为——BM 库接平台与否的评审须以此为准(`平台查询流程-HTTP形式.md` §4.2 留痕链)。

**取回即扩散边界(路径 B/C 下的附加约束):** 保密内容一旦被检索返回,会落入平台的会话记录、模型调用载荷与会话工作目录,且会话历史会作为后续对话的持续上下文。因此:
- BM 检索结果的去向须有明确规定——`[ASSUMPTION: BM 库内容不得进入非 BM 会话;该约束在 v1 依靠提示词与会话纪律承担,不构成技术强制]`。
- 保密内容的留存口径须在安全评审中一并确认,且**至少写定一条**不得留白的约定(平台侧的留痕清单见 addendum §4.6)。
- **source 页的可见性取舍**:消费面能读到 source 页(即原料的摘要与出处),这是"答案带来源"这一核心价值的实现方式;但它同时意味着保密文档的摘要对消费面可见。该取舍已在 FR-13 中显式声明,不在 v1 收窄。

### 9.2 凭据边界

| 允许落点 | 禁止面 |
|---|---|
| 流水线配置的凭据文件(宿主,0600);库配置中的**环境变量引用** | 库的版本控制历史;MCP 服务的环境变量块(会被复制进每用户每会话的配置文件,同文件还含平台自身的密钥与数据库连接串);原料区;**告警与日志** |

- 建图模型使用**专用低权凭据**,与平台交互凭据分离。
- **禁止字面量密钥**:库配置只允许引用环境变量名,不允许写密钥字面值——字面值会经由库仓库的历史永久留存,一旦提交过,轮换也无法真正撤销暴露。凭据来源与轮换/吊销责任人在部署期指定。
- BM 告警收件人限定。
- 凭据文件与库目录权限:库 0750(BM 独立组)、凭据文件 0600、日志目录 0750。

### 9.3 内容边界(内外有别)

- **外发告警消息**(Mattermost):只含批次 ID + 源 + 门代码 + 计数;**禁止**文档标题、路径、正文。
- **本地运行日志**(宿主内):为排障保留完整明细(含文档 key/路径),敏感性由文件权限承担(与 BM 库同域 0750)。
- 日志与库目录权限:库 0750(BM 独立组)、凭据文件 0600、日志目录 0750。

### 9.4 审计与决策可追溯

- 每个 SRC 保留原料出处(源系统 key 随包落盘)——任何知识页都能回答"这条来自哪"。
- 每个批次可回答"这批做了什么、谁跑的、什么时候、结果如何"。
- 原料不可变提供**来源可审计性**:任意历史批次的输入可精确重建。
- 流水线**全部写入只经写侧工具**——绕过工具的直接文件写入由门第 4 项检出。`[NOTE FOR PM]` **拦截钩子的现状须如实记录:钩子脚本存在,但当前未接线到会话设置**;且即便接线,它也**只覆盖交互会话的编辑动作**——对 Python 流水线完全无效。因此本系统的写径纪律**不能依赖钩子**,真正的兜底是:门第 4 项(事后检出)+ 代码评审红线 + 原料不可变。接线钩子是实施项,不是既有保障。违规后果不可逆(索引重建救不回)。

## 13. 运行要求与交付路线

### 13.1 交付阶段与出口标准

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| P0 单源骨架 | 一个源打通全链路;okf-kb 侧完成只读补丁 + 冒烟 + 服务常驻;平台侧完成 1 条 server + 1 个专属 agent | 端到端单库可问答;门全绿;两类冒烟通过;召回基线评测完成 |
| P1 四源铺开 | 其余三源逐一上线(每源重走 P0;BM 加白名单与人审) | 4 库 4 server 验收清单(§6.1)全部通过 |
| P2 调度与告警 | 定时编排 + 增量水位线 + 告警接线 + 心跳/陈旧度 + 告警演练 | 达到 SM-3 的"连续 N 个计划批次成功";告警演练触达 |
| P3 运维完善 | 恢复演练、升级流程演练、巡检基线固化 | 演练记录归档 |

实施前置依赖:§14 的实施前验证项。`[NOTE FOR PM]` R3(模型端点实测)是 P0 的唯一 go/no-go 前置——模型不可用则建图代理无法工作,整条链路不成立。

### 13.2 运行要求(上线后)

- **SLA:** 消费面 7×24 可用;流水线按约定节奏产出批次,超时无成功批次即告警。
- **恢复:** RPO ≤ 1 批、RTO ≤ 2 小时;每季度一次恢复演练。
- **备份:** 恢复域三者同域备份(库 + 流水线状态 + 流水线配置)。
- **日志保留:** ≥ 90 天且含轮转(与平台既有 30 天口径并存,须在文档中注明两套口径);轮转有明确责任人。
- **巡检:** 平台侧服务错误日志与库状态查询纳入巡检项;巡检项本身在 P3 固化为清单。

### 13.3 变更管理与不可放宽项

- **库格式规范不得放宽**:格式校验配置只允许按初始化契约**收窄**,不允许放宽规则以让批次通过。
- **消费面返回形状**属受版本控制配置,变更需记录。
- **门清单**修改需评审,单一来源不可绕过。
- **升级窗口**:停只读服务且无批次运行;窗口外不得替换工具目录。
- **回滚**:保留上一版工具目录整份用于回滚。
