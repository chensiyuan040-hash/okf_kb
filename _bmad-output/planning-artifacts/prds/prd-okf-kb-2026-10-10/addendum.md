## 2. 被拒方案与理由

### 2.1 用写侧工具的"内置自动编译路径"替代建图代理 —— 拒绝

**考虑过的做法:** 直接调用写侧工具的内置自动编译路径(`wiki_ingest` 的自动分支),由其内部子代理完成"读原料 → 生成知识页 → 提交"。

**拒绝理由(实测):** 该内部子代理**无工具可用**(唯一工具是"提交综合页"),系统提示词只有"忠实摘要",没有任何建图纪律提示词。后果:
- 不挂体系枢纽 → 产出页在体系树中不可枚举;
- 按标题精确匹配去重 → 概念分叉(同一概念产生多页);
- 每页只生成 1 条链接 → 互链密度不达标;
- 页面状态写为非枚举值 → 格式模式校验必挂。

**结论:** 其产出**通不过质量门**,不能作为全自动链路的建图者。改为**生产线建图代理**(FR-9):由编排器驱动 LLM 循环调用工具,带"先搜后建"纪律提示词,批内做状态归一。

**代价(已接受):** 建图质量上限 = 跑建图的模型上限;需要维护提示词资产。

### 2.2 用平台自带调度器编排 —— 拒绝

**考虑过的做法:** 复用平台的作业调度能力。

**拒绝理由:** 平台调度器的作业体与进程边界**都在平台容器内**。复用即让建库负载进入平台进程空间,违背"生产线与平台解耦"(AD-4):平台故障会波及建库,建库负载会挤占平台资源,凭据边界也会交叉。

**结论:** 调度用宿主 cron / systemd timer(§12)。

**代价(已接受):** 平台能力被分裂为**两套调度栈**——建库侧(宿主 cron/timer)与平台侧作业的排障入口、告警口径、日志位置各自独立,运维文档须分别交代;平台 UI 不会显示库状态与上次批次,**将来若要在平台界面看建库健康度,须另开接口**(不在本项目范围)。

### 2.3 消费面暴露只读结构层的检索能力 —— 拒绝

**考虑过的做法:** 在消费面额外提供结构层的检索(带体系语境的检索),让 agent 能拿到"这个页属于哪个体系分支"的上下文。

**拒绝理由:** 会形成**双 MCP 面**(同一库两个服务、两套契约、两处版本管理),运维与验收复杂度翻倍。

**代价(已接受,列 PRD §6.2):** 弱模型可能因缺少体系语境而误用知识。**回退条件:** 观察到该现象时重新评估。

### 2.4 向量语义检索作为首发能力 —— 延后(非拒绝)

**理由:** 先上线词法检索;是否引入由**可测量的读数**决定(黄金问题集命中率,FR-20),不由偏好决定。内网环境下向量检索还引入额外的模型依赖与容量占用。

**启用时的硬约束:** 索引重建**禁止**使用"全量"模式——内网环境会触发模型下载而必然失败;必须显式指定组件范围。

### 2.5 物理隔离 / 文件级强权限 —— 不做

**理由:** 需要平台侧的文件系统级改造(违反"平台零改动"),且与"平台无库级授权"的现状叠加后收益有限。改为 §9.1 的决策点处理——要么平台侧做**请求路径上的授权校验**,要么**书面接受**暴露面。

### 2.6 每源内的"重建到新库再切换" —— 澄清语义

架构中的"全量"与"重建"是两个不同动作,PRD 中容易混淆,此处钉死:

- **全量对账** = 忽略水位线**重扫源**以发现漏捕/删除/改名,**不重捕**内容未变条目(FR-5)。
- **按源重建** = 新库目录 + 重新绑定服务,**不在同一库内执行**——因为原料不可变(AD-2),"在同一库内重来一遍"在语义上不成立。

### 2.7 拆出"保密库的可共享子集" —— 拒绝

**理由:** 与"一源一库"的库边界冲突(AD-1)。子集判定本身需要人工分类,收益不抵复杂度。

## 4. 实施期工程约束(机制与传输)

*以下为"怎么做"的硬性细节,实施者必须遵守;PRD 不重复。*

### 4.0 仓库边界与提交范围

**两个层级的仓,边界必须分别钉死。**

**① okf-kb 顶层仓(本仓)** — `.gitignore` 至少排除:

```
vaults/          # 每库是独立仓,不由顶层仓跟踪
pipeline/state/  # 水位线/keymap 等运行时状态
logs/
raw-inbox/*      # 人工进料口
```

**② 每 vault 独立仓**(`vaults/<源>/.git`)— 提交范围为 `wiki/ + raw/ + meta/(除 qmd/) + .iwe/ + 设置文件`;`.gitignore` 至少排除 `meta/qmd/`(生成物,可重建)与一切承载密钥的文件(`.pi/settings.json` 若含密钥引用则只入键名不取值,须逐库确认)。**禁止 `git add -A`**——以路径清单显式提交,提交信息带 `batch=<ID>`。

**③ 供应链留痕:** 记录所用写侧工具包的版本,**至少须为含 0.11.8 修复形态的版本**(CVE-2026-102911:≤0.11.7 的 capture url 命令存在注入面);升级时保持该断言。注:bundle 内含修复形态,但其哈希无法独立复核;残余参数注入面(外部命令未用 `--` 分隔)须在调用封装层消解。

### 4.1 平台接入的实测形态(2026-10-14 起:HTTP)

- **传输:** **HTTP**(Streamable HTTP 常驻服务,`LLM_WIKI_HTTP=1`;服务跑在 okf-kb 服务器上,每库一个,端口 8901-8904)。平台按 url 连接——`McpServerConfig` 为 transport/http、url、headers、timeout;**知识库进程不在平台侧拉起,库文件不出 okf-kb 服务器**(旧 stdio 的"容器内子进程 + 继承容器视图"形态作废)。
- **环境变量:** HTTP 形态下平台侧**不传 env**——全部在服务端配死:`WIKI_ROOT`=`WIKI_HOME`(关个人库合并的唯一防线)、`LLM_WIKI_READ_ONLY=1`、`LLM_WIKI_HTTP=1` 与端口/监听地址。平台 DB→config 转发支持 `headers`,可用于前置认证反代。
- **命令形态:** 不适用(无 `command`;旧 stdio 的"容器内绝对路径"要求作废)。
- **超时:** 数据库层默认值不生效(实际回落到更长的默认值)。必须显式配置。
- **工具命名:** 平台对服务名做字符归一(连字符转下划线),呈现为 `mcp__okf_wiki_<源>__<工具>`;管理侧显示的集合名称保留连字符。两者口径不同,排查时勿混。
- **配置错误是静默的:** 服务名写错、未启用、未绑定 → 该会话**没有工具但不报错**。只能由启动冒烟兜住。服务未启动/不可达 = 平台连不上(报连接错误)——保密库"不开服务即不可达"即此机制。

**5 工具契约的来源(FR-16 表的依据):**

- `wiki_recall` / `wiki_search` / `wiki_status` / `wiki_lint` 四个工具来自上游工具包(`docs/pi-llm-wiki/api.md`),契约按上游现状记录:`wiki_recall` 默认 `max_results: 5`、上限 10,返回 `{id, title, type, preview, path, score}`;`wiki_search` 精确匹配登记表、无打分,返回 `{id, title, type}`;`wiki_status` 无入参,读**预建元数据**、不扫文件,返回 `{totalPages, byType, orphans, gaps, health}`;`wiki_lint` 库健康扫描(入参 `auto_fix` 可选)——**其写行为实测见 PRD FR-13**(默认调用即写报告与 gaps.json;`auto_fix=true` 追加写元数据并可建 stub 页)。
- `wiki_read` 是**本地补丁新增**的工具(见 CHANGELOG 本地补丁段):上游 `wiki_recall`/`wiki_search` 只返回约 120 字符的 `preview`,沙箱消费 agent(工具面仅 MCP)拿不到页全文,故补丁新增 `wiki_read(page_id, offset?, limit?)` 读整页,长页按字符窗口分页(默认 6000、上限 20000,响应带 `has_more` 与续读 `offset`),只开放 `wiki/` 层并拦截路径穿越。**升级重打 bundle 后需重打此补丁**——它是补丁序列的一环,由工具集冒烟守护(PRD FR-13/FR-22)。

### 4.2 运行形态

- 建图代理与工具 spawn 一律以**库根为工作目录 + 显式库根环境变量**;不得依赖用户级全局配置。
- 流水线运行时为宿主侧专用虚拟环境,**离线可安装**——实施前须钉死运行时版本与依赖来源。
- 每批设整体时限;单次工具调用设显式超时。
- 调度:单一调度器串行四源,或使用文件锁防止定时任务重叠。

**库配置必设键清单**(FR-9 的"必设键全部显式声明"引用的即此表;缺任一键即初始化缺陷,因多个键的**默认值是陷阱**):

| 键 | 必须显式设置的值/理由 |
|---|---|
| `taskModel` | **对象** `{provider, id}`——字符串形态会被**静默忽略**,不会报错 |
| `taskModelBaseUrl` | 模型服务地址(部署期与平台 `VLLM_BASE_URL` 对齐) |
| `taskModelApiKeyEnv` | 指向环境变量名,**禁字面 key**(见 PRD §9.2) |
| `synthesisLanguage` | `"zh"`——默认英文,而四源语料全为中文;不设即产出英文页 |
| `wikilinkValidation` | `"strict"`——默认 `warn`,链接错误不会拦门 |
| `synthesisMaxTokens` | 默认 16384 偏小,中文长文存在截断风险,须按实测上调 |
| `recallLinksThreshold` | 召回链路的链接阈值(消费面返回形状的一部分) |

*以上逐字引自概要设计 §5.6;该处为唯一权威来源,实施时以它为准。*
`~/.pi/agent` 用户级全局设置**禁止依赖**——每 vault 的 `.pi/settings.json` 是运行参数唯一来源。

**写锁元数据与人工会话顺序**(FR-7 的锁文件内容):

- 锁文件含 `{pid, 批次 ID, 获取时间, 来源: pipeline|session}`——排障时据此判定"谁持有、哪一批"。
- **人工会话 → 先停 timer,再显式取锁**——顺序不可颠倒,否则定时任务可能与人工操作并发。
- 定时任务侧可用 `flock -n` 保证不重叠。

### 4.3 索引与消费链路的关系(澄清)

**词法索引不是消费链路的必要条件。** 消费面检索实际读的是生成物登记,而非索引本身;索引刷新由写侧的工具触发。因此:

- 索引在只读服务下损坏时,消费侧**不能自愈**,但**召回仍应可用**——这正是"库坏"与"库空"需要靠冒烟区分的场景。
- 旧口径"只读补丁必须显式跳过启动期的索引恢复"**作废**(2026-10-14 对照代码:补丁未实现该跳过;实测服务启动/重启本身不写库,该条无必要)。
- 数据流中的"索引刷新"步骤归属**写侧**,消费侧只报告不修复。

### 4.4 禁用清单

| 禁用项 | 理由 |
|---|---|
| 索引重建的全量模式 | 内网会触发模型下载,必然失败 |
| **跨版本原地升级索引存储** | 索引存储格式随版本变化,**升级工具包版本时不得在原库原地升 qmd**——走"新库重建后替换"或显式指定组件重扫;升级 checklist 须含 vault 兼容项 |
| 向量索引的自建工具 | 内网不可用;若引入向量,走平台既有嵌入服务 |
| 写侧工具中的"监听"类工具 | 全自动场景误用 |
| 写侧工具中的"回写/记录"类辅助工具 | 自动链路不调用——这批工具面向人工会话,在流水线中无人判读其输出,调用即为噪声 |
| 结构层的迁移类命令(normalize / extract / inline / squash) | 迁移期之外禁用;确需时先空跑 |
| 密钥字面量进入库配置 | 见 PRD §9.2 |

### 4.5 库初始化契约(每库一次)

初始化按固定序列执行并逐项确认;其中"格式校验绑定收窄"是**必做项**——工具自动维护的目录页形态与格式规范存在固有冲突,不收窄则模式校验永久报错。初始化动作只允许对空库执行一次,重跑视为变更需人工确认。

**目录约定(复数)** — 知识页按类型分目录,目录名为**复数**:`concepts/`、`entities/`、`analyses/`、`requirements/`、`syntheses/`、`sources/`。单复数口径须与格式校验 schema 一致,初始化时一并钉死。

**原料区布局** — 每个源包占一个目录 `raw/sources/SRC-<ID>/`,内部含:原始正文文件、来源元数据(URL/标题/抓取时间/源系统标识)、内容指纹。源包**写入后不可变**;同一逻辑条目的重捕产生**新源包**,不覆写旧包。

### 4.6 平台侧留存与留痕(不属本项目交付面,须在安全评审确认)

平台自身会产生以下留痕面,本项目的加密/边界约定**不覆盖**它们,须在安全评审中一并确认口径:

1. 会话记录与调用载荷(不截断)、工具调用日志(未脱敏)、agent 运行日志;
2. 平台凭据文件全局单例(生产线若复用同一凭据,须约定轮换/吊销是否两处同步);
3. 平台侧保留期口径(现状 30 天)与本项目 ≥90 天的差异,须在运维文档中并列注明。

**约定下限:** 至少写明"BM 相关调用**不进入**平台通用会话/日志留存"或给出等价的替代控制——不留白。
