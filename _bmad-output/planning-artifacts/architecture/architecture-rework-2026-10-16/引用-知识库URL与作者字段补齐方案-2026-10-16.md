## 1. 现状诊断

### 1.1 结论

知识库**没有结构化保存**原文 URL 和作者信息:

| 数据层级                             | 现状                                                         |
| ------------------------------------ | ------------------------------------------------------------ |
| `raw/sources/*/manifest.json`        | 有 `file_path`(本地路径),无 `url`、无 `author`               |
| `wiki/sources/SRC-*.md`              | frontmatter 仅 `type/title/status/raw_path/source_id/format/captured`,无 url/author |
| `wiki/` 知识页(concepts/entities 等) | 53 页用 `source: [SRC-...]` 引用源 ID;0 页使用 `url:`/`author:`/`sources:`/`resource:` |
| `meta/registry.json` 等投影          | 仅 type/title/source(SRC-ID)/created/updated                 |
| 正文 `extracted.md`                  | 仅 20 个源首行有 `> 来源: Confluence ~chensiyuan/标题 (页面ID X, vN)`(**自由文本**,不可检索) |

### 1.2 根因

1. **扩展本身支持 URL,但本次导入没用它**:`wiki_capture_source(url=...)` 会把 URL 自动写入 manifest 并渲染为 `> _Original: [url](url)_`(见 `tools/pi-llm-wiki/mcp-server.mjs` 的 `urlCaptureSource` 与 `buildSourcePageSkeleton`)。本次 111 个源全部用 **file_path 方式**导入 Confluence 导出的本地 markdown,`fileCaptureSource` 的 manifest 只有 `file_path`,URL 就此丢失。
2. **扩展不支持 author**:`urlCaptureSource`/`fileCaptureSource`/`textCaptureSource` 的 manifest 均无 author 字段。
3. **规范早已预留字段但未落地**:OKF 规范 SPEC §5.1 定义 `sources[].author`/`sources[].resource`;`.llm-wiki/wiki/.iwe/schemas/okf.yaml` 也已定义 `sources[].author`。但实际只用了简化的 `source: [SRC-...]`,未用到出处字段。
4. **采集源头已不可访问**:`/home/chensiyuan/confluence-mirror/` 已不存在,无法重新抓取,只能从现有数据反推。

### 1.3 可回填性验证(已实测)

`raw/sources/` 共 **111 个源**,全部可反推出处:

| 来源                                                         | 数量 | 可提取信息                                                   |
| ------------------------------------------------------------ | ---- | ------------------------------------------------------------ |
| 正文首行 `> 来源: Confluence ~chensiyuan/标题 (页面ID X, vN)` | 20   | 平台、空间 `~chensiyuan`、**页面标题**、pageId、版本号       |
| manifest `title`/`file_path` 文件名前缀 `<pageId>_标题.clean.md` | 91   | pageId(正则 `^(\d{5,})[_\s]`)、空间(路径 `/md/{space}/` 段)、标题(去 ID 前缀与 `.clean.md` 后缀) |

- **pageId 提取成功率:111/111**
- 空间分布:`chensiyuan`(个人空间)20 个、`js`(团队空间)91 个
- 版本号:`v1`×12、`v2`×4、`v3`×3、`v10`×1(仅个人空间源有;团队空间源无版本信息)
- 正文中出现的 Confluence 域名均为 **http**(`http://wiki.wangankeji.cn/pages/viewpage.action?pageId=...`),无 https
- 正文/导出数据**无作者字段**(仅 7 个文件出现"作者/创建者"字样,均不可解析),作者只能按空间归属推断

## 2. 目标字段设计

回填后的 `wiki/sources/SRC-*.md` frontmatter(在现有基础上追加,不动既有字段):

```yaml
---
type: source
title: <清理后的页面标题>        # 例如 "设计文档生成" (去掉 ID 前缀和 .clean.md)
status: stable
raw_path: raw/sources/SRC-YYYY-MM-DD-NNN/extracted.md
source_id: SRC-YYYY-MM-DD-NNN
format: markdown
captured: YYYY-MM-DD
url: http://wiki.wangankeji.cn/pages/viewpage.action?pageId=70222502
page_id: "70222502"
source_platform: confluence
space: js                          # ~chensiyuan 个人空间源记为 chensiyuan
author: chensiyuan                 # 仅可确证作者填写(见 §3.3);团队空间源省略
source_version: v1                 # 仅个人空间源("来源"行含版本)填写;团队空间源省略
---
```

正文标题下加一行(与扩展 skeleton 渲染格式一致):

```markdown
# 设计文档生成

> _Original: [设计文档生成](http://wiki.wangankeji.cn/pages/viewpage.action?pageId=70222502)_
```

**作者策略(用户已确认):一律留空,仅可确证者填。**

- 个人空间源(`~chensiyuan`):作者 = 空间所有者 `chensiyuan`,可确证 → 填写。
- 团队空间源(`js`):导出数据无具体作者,不冒充 → 省略 author,仅记 `space: js` 供追溯。

## 3. 历史数据回填

### 3.1 建议产物

新增脚本:`okf-kb/scripts/backfill-provenance.py`

```
用法:
  python3 scripts/backfill-provenance.py --wiki-root <库目录>            # 执行
  python3 scripts/backfill-provenance.py --wiki-root <库目录> --dry-run  # 预览,不写盘
  python3 scripts/backfill-provenance.py --wiki-root <库目录> --with-raw # 可选:同时回填 manifest.json
```

要求:幂等(重复执行结果一致);按 SRC-ID 逐个输出"改动/跳过/异常"一行;dry-run 与执行输出同构。

### 3.2 解析逻辑(优先级从高到低)

对每个 `raw/sources/SRC-*/`:

1. **读 extracted.md 前 8 行**,匹配 `^>\s*来源[：:]\s*(.+?)\s*\(页面ID\s*(\d+)\s*,\s*(v\d+)\)`
   - 命中 → 得 `platform=Confluence`、`space`(取 `~xxx` 或首段)、**页面标题**、`page_id`、`source_version`。
2. **否则**,从 `manifest.title` → `file_path` 的 basename 匹配 `^(\d{5,})[_\s]` 提取 `page_id`;`space` 取 `file_path` 中 `/md/([^/]+)/` 段;标题 = 文件名去掉 `<pageId>_` 前缀与 `.clean.md`/`.md` 后缀(若为空则保留原 title)。
3. `url = http://wiki.wangankeji.cn/pages/viewpage.action?pageId={page_id}`
4. 若 page_id 提取失败 → 该源标记 `FAILED`,跳过并告警(不应发生,实测覆盖 111/111)。

### 3.3 写入内容

| 目标                         | 写入                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| `wiki/sources/SRC-*.md`      | frontmatter 追加 `url`/`page_id`/`source_platform`/`space`(+`author`、`source_version` 按 §2 规则);正文 H1 后插入 `> _Original:` 行(不存在才插) |
| `meta/registry.json`         | 对应 source 条目追加 `url`/`author`(保持投影与页面一致;若扩展重建会覆盖,可接受——它不读 url/author 以外的字段) |
| 知识页(concepts/entities 等) | **不改**。`source: [SRC-...]` 引用链已能追到带出处的 source 页 |

### 3.4 是否回填 `raw/sources/*/manifest.json`(待执行前再定)

- **WIKI_SCHEMA.md 归属规则**:`raw/**` 为 extension-owned、`immutable after capture`——直接改 manifest 违背既有约定。
- **只改 wiki 层**(默认推荐):合规、风险最小;source 页是人/模型可编辑知识层,url/author 放这里即可检索、可溯源。
- **同时回填 manifest**(可选 `--with-raw`):让机器可读元数据也完整,利于后续检索索引直接读 url;代价是一次性打破 raw 不可变约定,并需在 `meta/events.jsonl` 追加一条记录说明(如 `kind: provenance_backfill`)。

> 注意:无论哪种选择,**不要改 extracted.md 正文**(它是抓取快照,正文第一行的"来源"自由文本保持原样)。

## 4. 后续流程固化(防止再丢)

### 4.1 模板

`wiki/.llm-wiki/templates/pages/source.md`(wiki 实际使用的模板)对齐扩展新版 V2 模板,frontmatter 增加:

```yaml
type: source
format: article # article | paper | note | video | ...
url: <原文链接>
author: <作者, 未知则省略>
```

正文增 `> _Original: [标题](url)_` 占位行。

### 4.2 约定文档

`wiki/.llm-wiki/WIKI_SCHEMA.md` 增补:

- source 页 frontmatter **必含 `url`**(web 源)与 `author`/`space` 之一;本地文件源至少回填 `page_id` + `source_platform`。
- 新源抓取规范:URL 源一律 `wiki_capture_source(url=...)`;本地文件源导入后,ingest 时由模型从文件名/内容提取 pageId 补齐 URL。
- 知识页引用维持 `source: [SRC-...]`,出处信息统一沉淀在 source 页,不在知识页重复。

### 4.3 Schema 机械把关(⚠️ 顺序敏感)

新建 `wiki/.llm-wiki/wiki/.iwe/schemas/source.yaml`(或扩展现有 okf.yaml):

```yaml
$schema: https://document-schema.org/draft/2026-06/schema
description: source 页必须有可追溯出处
frontmatter:
  type: object
  required: [type]
  properties:
    type: { const: source }
    url: { type: string, pattern: '^https?://' }
    page_id: { type: string }
    source_platform: { type: string }
    space: { type: string }
    author: { type: string }
```

在 `.iwe/config.toml` 的 `[schemas]` 追加绑定:

```toml
[schemas.source]
match = ["sources/**"]
```

**注意**:必须**先执行回填(§3)、再启用该 schema 约束**,否则已存在的 111 个 source 页全会校验失败。启用后跑 `iwe schema validate` 确认通过。

### 4.4 巡检告警

`okf-kb/scripts/kb-patrol.sh` 的"分叉线索/verified 腐坏"段新增一条机械检查:

- 统计 `wiki/sources/*.md` 中 frontmatter 缺少 `url` 的页数,>0 时进入 ALERT。

### 4.5 新源抓取 SOP

1. 网络来源 → `wiki_capture_source(url=...)`(扩展自动落 url + Original 行)。
2. 本地文件来源 → 先看文件名/路径能否提取 pageId,能则导入后回填 URL;不能则 source 页写明 `source_platform` 与可得信息,`url` 留空并标注 `url_unknown: true`。
3. 入库即校验:`iwe schema validate` + `kb-patrol.sh` 巡检兜底。

## 6. 风险与取舍

| 项                  | 说明                                                         |
| ------------------- | ------------------------------------------------------------ |
| URL 为内网 http     | 与正文一致;若后续 Confluence 换 https 或迁移域名,URL 会失效,需再回填一次(可留 page_id 便于重建) |
| 团队空间无作者      | 只能记 `space: js`,不冒充具体作者;如需精确作者需回到 Confluence 用 API 导出(当前不可行) |
| raw 不可变约定      | 默认不动 raw/;若选 `--with-raw` 需在 events.jsonl 留痕       |
| source 页被扩展重建 | capture 时才重建 skeleton;存量 source 页归 wiki 层所有,不会被自动覆盖 |
