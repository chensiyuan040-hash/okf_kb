# 平台查询流程(HTTP 形式)

> 日期:2026-10-14 · 配套:`平台侧改动-HTTP接入片段.md`(平台团队执行) · 读者:okf-kb 侧 + 平台侧
> 一句话:**知识库是跑在 okf-kb 服务器上的 HTTP 服务;平台智能体是它的客户端。平台上查库 = 智能体向该服务发 HTTP 请求。**

## 一、角色与部署构成

| 角色 | 在哪 | 干什么 |
|---|---|---|
| 知识库 HTTP 服务(每库一个) | okf-kb 服务器(建议 systemd 常驻) | 持 vault 目录,只读模式配死;监听端口(8901-8904),响应 `/mcp` |
| 建库会话 | okf-kb 服务器(本地 stdio) | 日常 capture→ingest→治理,写侧;**不经过 HTTP 面** |
| 平台 backend + agent_worker(hermes) | 平台侧 | 会话管理、消息落库;agent 运行时按 URL 连知识库、把工具呈现给 LLM |
| 平台用户 | 浏览器 | 在平台界面选智能体、提问、看回答 |

库文件**只存在于 okf-kb 服务器**,平台任何容器/机器上都没有 vault 副本;平台只看到 HTTP 接口。

## 二、普通库的查询流程(日常形态)

```
用户浏览器          平台 agent_worker(hermes)         okf-kb 服务器
   │                       │(进程启动时已按 URL 连上,          │
   │                       │ 工具列表里有 mcp__okf_wiki_*)     │
   │ 提问:"部署规范是什么"   │                                  │
   ├──────────────────────>│                                  │
   │                       │ LLM 判断需要查库                   │
   │                       │ POST http://okf-ip:8901/mcp      │
   │                       │  wiki_recall("部署规范")          │
   │                       ├─────────────────────────────────>│
   │                       │        <── 页面列表(preview)──────┤
   │                       │ 命中相关页 → wiki_read 读全文      │
   │                       ├─────────────────────────────────>│
   │                       │        <── 页面全文 ──────────────┤
   │                       │ LLM 组织回答(带出处)              │
   │  回答 + 出处            │                                  │
   │<──────────────────────┤                                  │
   │        ⚠ 会话消息 + 工具返回内容 → 落平台 PG 数据库(磁盘)  │
```

分步说明:

1. **服务先起好**:okf-kb 服务器上每库一个 HTTP 常驻服务(`LLM_WIKI_HTTP=1` + `LLM_WIKI_READ_ONLY=1`)。服务跑着 = 平台能查;服务停着 = 平台连不上。
2. **平台侧注册与绑定**:管理员在后台 `mcp_server_configs` 注册 url 型 server;智能体配置里勾选绑定。**agent 进程加/删 server 需重启生效**(hermes 无热重载)。
3. **会话开始**:用户提问 → 平台把消息交给 agent_worker;hermes 的 MCP 客户端早已连着 URL,把知识库工具注册为 `mcp__okf_wiki_<source>__wiki_recall` 等呈现给 LLM。
4. **查库**:LLM 按需调用——`wiki_recall`(定位)→ `wiki_read`(读全文)。每步都是一次 HTTP POST 到 okf-kb 服务器;服务读 vault、返回内容。写侧工具在服务端**物理不存在**,平台侧无从绕过(唯一例外:`wiki_lint` 带回写行为——写报告/元数据、可建 stub 页,见概要设计 §6.1)。
5. **留痕**(平台侧固有):会话消息与工具返回内容持久化到平台 PostgreSQL(磁盘);回答经平台模型网关产生。

**服务不可达时的表现**:hermes 对失败连接做有限重试(指数退避,上限后放弃);已建立的连接在服务恢复后会自动重连。即——库没开,智能体查不到(报连接/工具错误),开了就能查。

## 三、权限与可见性(平台既有事实,如实知悉)

- 平台**无 MCP 库级授权**:任意登录用户可在会话参数 `mcps` 里挂载任意 active server——智能体绑定只是默认值,不是访问控制(chat.py:1018;ARCHITECTURE-SPINE AD-1 已记录,「BM 库对平台全员可见、可查」为**已接受的逻辑隔离风险**)。
- HTTP 面**无内置认证**:绑定 `0.0.0.0` 后,内网能访问端口的机器都可查——访问控制靠防火墙/认证反代(见接入片段 §5)。
- 两道防线配合:服务端只读(防写;已知例外 `wiki_lint`,见概要设计 §6.1)+ 网络面收敛(防未授权读)。

## 四、保密库(BM)的查询流程

保密库遵循同一 HTTP 形态,但多了封存/解封循环,且**留痕结论决定它能不能接平台**。

### 4.1 开 / 关

```
平时(封存态):  密文包在磁盘(~/.okf-secret/vault.tar.gz.gpg);服务不跑 → 平台查不到
要用时(开启):  unseal(口令,解到内存盘) → serve 起 8904 服务(只读,@内存盘)
用完(封存):    stop 停 8904 服务 → seal(重新加密打包) → 内存/磁盘零明文
```

「开服务/停服务」= `okf-secret-vault.sh serve` / `stop`(2026-10-14 已落地并全流程实测;服务在跑时 `seal` 与 `unseal --force` 会被拒绝——先 stop)。

### 4.2 留痕链(开给平台查时,保密内容会到哪里)

| # | 环节 | 保密内容是否经过 | 落磁盘? |
|---|---|---|---|
| 1 | okf-kb 服务器内存盘(vault) | 是(源头) | 否(tmpfs) |
| 2 | 平台 agent_worker 收到 HTTP 响应 | 是 | 进程内存,一般否 |
| 3 | **平台 PG 会话消息表**(工具结果 + 回答) | 是 | **是——保密内容进平台数据库** |
| 4 | 平台模型网关(LLM 推理) | 是(prompt 含库内容) | 取决于网关部署 |
| 5 | 用户浏览器(回答展示) | 是 | 可能(浏览器缓存) |

与本地隔离会话(secret-vault run)相比,第 3/4 环是平台侧**不受 okf-kb 工具控制**的新增留痕面。

### 4.3 结论(分环境)

| 平台环境 | BM 库能否开给平台查 |
|---|---|
| 普通内网环境(会话落库、模型网关无保密措施) | **不能**。查保密库只用本地隔离会话(secret-vault run);平台侧 BM 服务不注册 |
| 保密受控环境(平台部署整体满足保密要求:库/盘加密、网关受控、审计合规) | **可以**。此时保密边界从"内存盘"上移到"整个平台环境",需平台侧出结论并承诺 |

## 五、与旧 stdio 方案的差异(为什么改)

| 维度 | 旧:stdio(已废弃) | 现:HTTP |
|---|---|---|
| 库文件位置 | 挂载进 backend 容器 | **只在 okf-kb 服务器**,平台零副本 |
| 平台改动 | compose 加 5 行挂载 + recreate | 后台注册 4 条 url 记录(平台代码零改动) |
| 进程 | 容器内 spawn 子进程 | 服务器常驻服务,平台只连线 |
| 对保密库 | 明文要进容器磁盘,**不可行** | 明文只在服务器内存盘;风险转移到平台留痕(§4.2) |
| 权限面 | 挂载面 = 权限面 | 网络面 = 权限面(防火墙/反代) |
